## 三、为什么端口是 13306 / 16379 而不是 3306 / 6379

宿主机可能已经有 MySQL 或 Redis 服务占用默认端口，所以 Compose 使用非默认端口。

**两个理由必须记住，面试会问：**

1. **环境隔离**：不干扰你已有的数据库，也不需要知道它的账号密码
2. **可移植性**：`docker compose up` 在任何机器上都能跑，不依赖宿主机装了什么

这是**作品集项目的硬要求**——面试官如果 clone 你的代码，必须能一键起来。用宿主机已有的数据库就做不到这一点。

## 四、为什么用 Flyway，不用 Docker 初始化脚本

两种常见做法：

| 做法 | 问题 |
|---|---|
| `docker-entrypoint-initdb.d/init.sql` | 只在**数据卷为空时**执行一次；改了 SQL 不会重跑，只能删卷重建；数据库版本无法追溯 |
| **Flyway 迁移脚本** | 每个变更是一个带版本号的文件，按顺序执行并记录在 `flyway_schema_history` 表；可追溯、可回滚、团队协作安全 |

**Flyway 的核心规则**：`V1__baseline.sql`、`V2__identity_schema.sql` —— `V` + 数字 + 双下划线 + 描述。

**已经执行过的脚本不许改**。改了会导致校验和不匹配，启动直接报错。要改结构就新增 `V3__xxx.sql`。

**面试会问**：
- "数据库表结构怎么管理的？" → Flyway 版本化迁移，已执行的脚本不可变
- "生产环境怎么发布？" → 迁移脚本随应用一起发布，启动时自动执行，失败则应用启动失败（fail-fast）

## 五、数据库设计的三条约定

写在 `V1__baseline.sql` 的头部注释里，后面所有表都遵守：

**1. 主键用雪花 ID，不用数据库自增序列**

```java
id-type: assign_id   // MyBatis-Plus 的雪花算法
```

理由：自增 ID 会暴露业务量（竞争对手能从订单号推出你一天多少单），且将来分库分表时无法保证全局唯一。雪花 ID 是 64 位长整型，趋势递增（索引友好）且全局唯一。

**2. 金额用 `NUMERIC(19,4)`，禁止 float/double**

```sql
settlement_amount NUMERIC(19,4)
```

`float`/`double` 是二进制浮点，`0.1 + 0.2 != 0.3`。金额上出现这种误差是事故。`NUMERIC` 是精确十进制。

Java 侧对应 `BigDecimal`。

**3. 每张业务表都有软删除 + 审计字段**

```sql
created_at / updated_at / created_by / updated_by / deleted
```

`updated_at` 由数据库触发器自动维护（`set_updated_at()`），应用层不需要手动赋值——**应用层能忘，数据库不会忘**。

## 六、多租户的设计

`t_enterprise` 是租户根，所有业务数据都挂在某个企业下面。

**关键规则（这条要背下来）**：

> 企业 ID **永远**从登录态（JWT）里取，**绝不**从请求参数里取。

```java
// 正确
Long enterpriseId = SecurityUtils.currentEnterpriseId();

// 错误 —— 攻击者改个 id 就能看别的企业的数据
Long enterpriseId = request.getParameter("enterpriseId");
```

这条规则在阶段 2 会具体体现。现在只需要记住：**越权防护靠架构，不靠开发者自觉**。

## 七、表结构说明（V1-V10 迁移）

| 表 | 作用 | 关键点 |
|---|---|---|
| `t_enterprise` | 企业/交易商 | 租户根。有 `trader_code` 交易席位号，审核通过后分配 |
| `t_user` | 平台账号 | `enterprise_id` 为 NULL 表示平台运营人员 |
| `t_role` | 角色 | `enterprise_id` 为 NULL 表示平台级角色（共享） |
| `t_permission` | 权限目录 | 平台定义，不分租户 |
| `t_user_role` | 用户-角色 | 关联表 |
| `t_role_permission` | 角色-权限 | 关联表 |
| `t_audit_log` | 审计日志 | **只增不改不删**，由 AOP 切面写入 |

V1-V10 按身份认证、顾问会话、商品库存、交易、结算合同、知识库、挂牌确认模式和规则手册逐步扩展。当前数据库是 MySQL 8.4：金额使用 `DECIMAL(19,4)`，数量使用 `DECIMAL(18,3)`，软删除过滤由查询负责；MySQL 不支持 PostgreSQL 的 partial index。

**为什么 `t_audit_log` 没有软删除字段？**
审计日志是合规要求，必须只增不改。给它加 `deleted` 字段反而是隐患——有人能"删掉"审计记录。

## 九、这一阶段面试会问什么

1. **"多租户怎么实现的？"**
   → 共享库共享表 + `enterprise_id` 列隔离，企业 ID 从 JWT 取而非入参
   → 追问："为什么不用分库分表？" → 数据量到不了，过早分片只增加复杂度

2. **"为什么用 MyBatis-Plus 不用 JPA？"**
   → 复杂查询（报表、对账）用 ORM 难以控制生成的 SQL；MyBatis 的 SQL 可见、可优化
   → 加分回答："简单 CRUD 用 MyBatis-Plus 的 `BaseMapper`，复杂统计查询我自己写 SQL"

3. **"软删除怎么做？有什么坑？"**
   → MyBatis-Plus 的 `logic-delete-field`
   → 坑：唯一索引会和软删除冲突，所以建索引时要带 `WHERE deleted = 0` 条件（见 `uk_enterprise_code`）

4. **"审计日志怎么记录的？"**
   → AOP 切面拦截 + 记录前后值 → 阶段 2 实现
