## 二、页面

| 路由 | 页面 | 说明 |
|---|---|---|
| `/login` | 登录 | 带开发账号快捷填充 |
| `/` | 首页 | 平台介绍、市场概览和公开挂牌信息 |
| `/market` | 行情 | 行情报价和价格趋势 |
| `/trading` | 挂牌交易 | 公开挂牌浏览；登录后处理自己的交易任务 |
| `/dashboard` | 工作台 | 登录后的个人工作台 |
| `/inventory` | 我的库存 | 当前企业的库存 |
| `/advisor` | AI 顾问 | 对话 + 调用链展开 |
| `/enterprise` | 企业信息 | 当前账号与企业资料 |
| `/knowledge` | 知识库检索测试 | 运营后台页面，需登录并持有 `admin:knowledge` 权限 |

**AI 顾问页是重点**：每条回答下方可以展开看**完整工具调用链**——调了哪个工具、入参是什么、返回了什么。

这不是装饰。一个关于平台数据的回答，可信度取决于产生它的那次查询。把调用链摊开给用户看，他才能核对数字，而不是只能选择相信。

## 三、四个关键设计

### ① 响应信封在拦截器里统一拆掉

后端所有接口都返回同一个信封：

```json
{ "code": 0, "message": "OK", "data": { ... } }
```

前端在 `api/client.ts` 里一次拆掉：

```ts
async function request<T>(config): Promise<T> {
  const response = await instance.request<ApiResponse<T>>(config)
  const body = response.data
  if (body.code !== 0) {
    notifyError(body.message)
    throw new ApiError(body.code, body.message)
  }
  return body.data       // 页面直接拿到 data
}
```

**好处**：页面里没有任何一处需要判断 `code`。业务代码只关心数据。

### ② token 存 localStorage——这是个有代价的选择

```ts
persist(..., { name: 'spotlink-auth' })
```

localStorage 里的 token **任何页面脚本都能读**。一旦有 XSS 漏洞，token 就被偷走。

更安全的做法是：refresh token 放 HttpOnly Cookie（JS 读不到），access token 只放内存（刷新页面就重新换一次）。

这里选 localStorage 是因为**用起来简单，且本地开发没有 XSS 面**。但这是**有意识的取舍，不是不知道**——面试被问到时要说得出上面这段。

### ③ Vite 代理，而不是配 CORS

```ts
proxy: { '/api': { target: 'http://localhost:8081', changeOrigin: true } }
```

浏览器只看到 `localhost:5173` 一个源，**根本不产生跨域**。后端其实也配了 CORS，但代理是更省事的那条路：不需要两边同步配置，也不会有预检请求。

### ④ 路由守卫不是安全边界

```tsx
if (!accessToken) return <Navigate to="/login" replace />
```

这只是**省一次无谓的请求**。真正的权限校验在后端——前端藏起一个页面，不构成任何保护。改一下 localStorage 就能"进去"，然后所有接口返回 401。

**这句话面试要能主动说出来**，它体现你分得清"用户体验"和"安全控制"。

## 四、踩的坑

| 坑 | 现象 | 解法 |
|---|---|---|
| antd 静态 `message.error()` 无效 | 控制台警告，样式丢失 | 静态方法读不到 App context，用 `App.useApp()` 拿实例再注册到全局 |
| `tsc -b` 与 `noEmit` 冲突 | 构建脚本报错 | 改成 `tsc --noEmit && vite build` |
| vite.config 用了 `node:url` | 类型检查找不到模块 | 装 `@types/node` |
| curl 发中文变 GBK | 后端返回 400 | 用 Swagger UI 或 Python 发请求 |

## 五、构建产物

构建产物会随页面和依赖变化，不把某次构建的文件名和精确大小当成稳定契约。2026-10-01 在当前代码上运行 `npm run build` 的结果约为：`react-vendor` 92.5 kB、`antd-vendor` 1.13 MB、业务 chunk 1.15 MB（gzip 分别约 31 kB、350 kB、380 kB）。Vite 会对超过 900 kB 的 chunk 给出提示，这属于当前已知的前端体积成本。

**分包配置**：

```ts
manualChunks: {
  'react-vendor': ['react', 'react-dom', 'react-router-dom'],
  'antd-vendor': ['antd'],
  'icons-vendor': ['@ant-design/icons'],
}
```

**为什么要分包**：不拆的话全部打成一个文件，改一行业务代码，用户就要重新下载整个 bundle。拆完之后 React、Ant Design 和业务代码分别缓存，改业务时不必重新下载 React 和组件库。

**关于体积**：Ant Design 会带入共享的 `rc-*` 底层代码，tree-shaking 只能去掉未使用模块。继续降低需要按页面拆分、动态导入或换轻量组件库，应该用实际构建结果和首屏性能数据决定，而不是只看文件名。

代码里把 `chunkSizeWarningLimit` 设成 900 并**写了注释说明原因**——这是"已知且接受的成本"，不是"没发现的性能问题"。

## 六、面试会问什么

1. **"前端怎么处理登录态？"**
   → JWT 存 localStorage，axios 请求拦截器自动加 Authorization 头，响应拦截器遇 401 清空登录态并跳登录页。
   → 追问"localStorage 安全吗" → 说出 XSS 风险和 HttpOnly Cookie 的替代方案。

2. **"跨域怎么解决的？"**
   → 开发环境用 Vite 代理，生产环境由 Nginx 同源部署。后端也配了 CORS 作为兜底。

3. **"为什么用 Zustand 不用 Redux？"**
   → 全局状态只有登录态一个，Zustand 的 API 更短，没有 reducer/action 那套模板代码。状态多了再换也不难。

4. **"前端怎么做权限？"**
   → 路由守卫只是体验优化，真正的控制在后端。前端藏菜单不等于有权限。

5. **"做过构建优化吗？"**
   → 分包（react / antd / icons / app 四块），业务代码改动不触发 vendor 重下；能说清 antd 体积的构成和为什么降不下来。

## 七、公开面：未登录也能读的部分

平台不能一进门就要求登录。一个连"这里有什么货、什么价、规则是什么"都看不到的网站，访客没有理由注册。

### 分界线不是"能不能保护"，而是"页面有没有东西可显示"

这条界线容易画错。直觉会把它当成安全问题——"哪些数据更敏感"——但真正的判据是**给一个没有企业归属的人看，这个页面能不能给出完整答案**：

| 页面 | 未登录看到什么 | 结论 |
|---|---|---|
| 首页 / 行情 / 挂牌大厅 | 完整内容 | **公开** |
| 知识库检索测试 | 运营索引状态和召回片段 | 需登录及 `admin:knowledge` 权限 |
| 我的库存 / 我的订单 / 合同 / AI 顾问 | **空的** | 要登录 |

后一组不是"被挡住了"，是**没有 `my` 可以查**。给访客渲染一个空表格，比直接告诉他"请先登录"更让人困惑。

所以 `RequireAuth` 的注释里写了两遍同一句话：**这不是安全边界**。真正的控制在后端。前端守卫只是免得用户白跑一趟。

### 后端：按 HTTP 方法放开，而不是按路径前缀

```java
private static final String[] PUBLIC_READS = {
        "/api/public/**",
        "/api/listings/market",   // 注意：不是 /api/listings/**
        "/api/categories/**",
        "/api/market/**",
        // 知识库已移入运营后台，不在公开读取清单中
};

.requestMatchers(HttpMethod.GET, PUBLIC_READS).permitAll()
```

**为什么必须带方法限定**：认证后的写接口就贴在旁边。

- `/api/listings/mine` 距离 `/api/listings/market` 只差一个路径段
- `/api/admin/knowledge/*` 由 `@PreAuthorize` 按权限码保护，不属于公开面

按前缀放开，等于把这两个一起放开了。`GET` 限定让"只读"这件事在配置里就是字面意思。

**验证要正反都做**——只测"公开的能访问"是不够的，那只证明了 `permitAll` 生效，没证明别的都没被顺带放开：

```
--- should be PUBLIC ---
  OK  200 /public/stats
  OK  200 /listings/market
  OK  200 /categories/tree
  OK  200 /market/quotes
--- should be PROTECTED ---
  OK  401 /listings/mine
  OK  401 /orders
  OK  401 /inventory-notes
  OK  401 /auth/me
  OK  401 /contracts
  OK  401 /advisor/conversations
  OK  401 /admin/knowledge/search
  OK  401 POST /admin/knowledge/embed-pending
```

知识库前端页面虽然挂在 `/knowledge` 路由下，但它是运营维护工具，不是访客规则手册：请求实际使用 `/api/admin/knowledge/stats`、`/search` 和 `/embed-pending`，分别需要 `admin:knowledge` 或 `admin:knowledge:embed`。顾问在服务端进程内直接调用 `KnowledgeService`，不经过这个 HTTP 页面。

### 前端：401 拦截器会把访客"踢出去"

这里有个不显眼的坑。客户端的 401 处理是**清空登录态并跳登录页**——对过期会话是对的，对访客就是灾难：

```tsx
const { data: myOrders = [] } = useQuery({
  queryKey: ['my-orders'],
  queryFn: () => fetchMyOrders(),
  enabled: signedIn,        // ← 少了这一行，访客一进挂牌大厅就被弹到登录页
})
```

挂牌大厅是公开的，但页面里同时挂着"我的订单"的查询。访客进页面 → 该查询发出 → 401 → **被踢到登录页**。用户会以为"公开浏览"是坏的。

**所以公开不等于少写代码**：公开页面里每一个属于登录态的查询，都要显式地关掉。

### 首页说什么

参考了同业平台（上海有色网的「安汇达」）对外呈现的方式：**市场规模、最新价格、在挂的货、规则在哪**。

```java
// 全部是平台整体口径，没有一条描述单个会员
SELECT COUNT(*) FROM t_enterprise WHERE deleted = 0 AND status = 1;   -- 入驻企业
SELECT COUNT(*) FROM t_order
 WHERE deleted = 0 AND status NOT IN ('PENDING_CONFIRM','CANCELLED');  -- 累计成交
```

**"累计成交"为什么要排除两个状态**：

- `CANCELLED` 是被撤销的，算进去就是虚报
- `PENDING_CONFIRM` 是**还没人答复的请求**，不是成交（这正是上一节 `MANUAL` 模式引入的状态）

`AUTO` 挂牌摘牌即成交、直接进 `CONFIRMED`；`MANUAL` 挂牌在挂牌方点头之前不进这个统计。

**金额由服务端格式化**（`3.2 亿元`）而不是丢给浏览器：首页和将来的报表必须对"亿元"是同一个口径，各round各的就对不上了。

## 八、公开面的追问

第六节那几条之外，这一段还会被问到的：

**"未登录浏览怎么做？"**
→ 按方法放开只读接口（`GET` 限定），公开面只放平台整体口径。
→ 加分：说清分界线不是"敏感与否"，而是"没有企业归属时页面能不能给出完整答案"。
→ 加分：说清公开页面里的登录态查询必须显式 `enabled: false`，否则 401 拦截器会把访客踢到登录页。

**"怎么验证没有放开太多？"**
→ 正反都测：公开的必须 200，**受保护的必须 401**。只测前者等于没测。
