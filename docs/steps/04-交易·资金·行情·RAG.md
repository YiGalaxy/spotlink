## 一、挂牌交易：法律定性决定了架构

### 挂牌是要约，摘牌是承诺

《交易管理办法》式的定义：

> **挂牌**：交易商预先公布要买卖商品的详细情况（名称、厂家、品牌、质量、价格、数量、交货地点、提提货方式），经审核后发布买卖信息。
> **摘牌**：对挂牌方发出的**要约进行应约（承诺）**的行为。

这不是文案，**整个代码库的形状由它决定**：

| 如果挂牌是"挂单" | 如果挂牌是"要约" |
|---|---|
| 需要撮合引擎配对 | 不需要，摘牌就是承诺 |
| 价格由引擎发现 | 价格由双方约定 |
| 集中竞价 → **期货特征** | 一对一合同 → **现货** |

所以这个项目里**没有任何撮合引擎**，这不是没做，是**不该做**。

### 挂牌不拿走货物，只预留

```java
// 卖方挂牌
listing.setFreezeId(freezeForListing(request, enterpriseId));
```

挂牌冻结 60 吨，卖方库存变成"可用 40 / 冻结 60"——**货主还是他**。撤牌或过期时解冻，货回到可用。

这就是为什么数量要拆成三个口径。

### 部分消耗：一笔挂牌可以分多次成交

卖方挂 100 吨，买方摘 30 吨，剩下 70 吨还要能继续卖。

`FreezeService.consumeInventoryPartial` 的实现方式是：**原冻结记录标记为已消耗，剩余量开一条新记录**，而不是就地修改数量。

```java
markConsumed(record);
if (remainder.signum() > 0) {
    // 新开一条记录，而不是改旧记录的数量
}
```

**为什么不改旧记录**：冻结记录是一条"某时刻预留了多少"的陈述。改写它就抹掉了"当时预留了多少"——而这恰恰是日后双方争执时要问的第一个问题。多一行不花钱，把痕迹留住才值钱。

## 一之二、两种成交模式：谁说了算，货什么时候动

上面那套「挂牌=要约、摘牌=承诺」是**挂牌交易**的定义。但市场上还有另一种同样合法的做法，区别只在一件事上：**发布挂牌算不算挂牌方已经同意了。**

| | `AUTO` 摘牌即成交 | `MANUAL` 需挂牌方确认 |
|---|---|---|
| 挂牌的法律性质 | **要约** | **要约邀请** |
| 摘牌是什么 | 承诺，合同当场成立 | 提出成交请求 |
| 谁最终拍板 | 没人能反悔 | 挂牌方 |
| **货权何时转移** | **摘牌那一刻** | **挂牌方确认那一刻** |
| 拒绝后怎么处理 | 只能协商解除合同 | 挂牌数量原样恢复，当作没发生 |

**为什么两种都要做**：只做一种，平台就没法解释自己。做 `AUTO` 却说"挂牌方可以不同意"，等于摘牌不是承诺；做 `MANUAL` 却在摘牌时就过户，等于确认这一步是摆设。

**这是发布时选定的，不是全局开关**——它是**要约本身的属性**，同一个卖家完全可能一张挂牌定死价格、另一张要自己点头。

```java
// 唯一分叉的地方，只判断一次
boolean awaitsLister = listing.awaitsListerConfirm();
Long goodsFreezeId = awaitsLister
        ? null                                              // 什么都不动
        : transferGoods(listing, quantity, buyerId, sellerId);
```

### 关键设计：`MANUAL` 摘牌时**不转移货权**

摘牌只做一件事——**把数量从挂牌上摘掉**（`remainingQuantity` 减掉），防止第二个买家摘走同一批货。冻结不动、库存单不动、买方拿不到任何东西。

于是冻结量始终覆盖「未成交部分 + 待确认部分」：

```
挂 100 吨 → 冻结 100，剩余 100，待确认 0
A 摘 30   → 冻结 100，剩余  70，待确认 30
B 摘 40   → 冻结 100，剩余  30，待确认 70
确认 A    → 冻结  70，剩余  30，待确认 40   ← 此刻才消耗 30 吨
```

**这个不变量是整套设计的可验证点**：任何时刻，冻结量都等于还没落定的全部货物。

### 沉默不是同意

挂牌方一直不答复怎么办？订单不能永远挂着，货也不能永远冻着。

- 摘牌时给一个 **答复截止时间**（`confirm_deadline`），取「确认窗口」和「挂牌有效期」中较早的那个——不能出现"承诺活过了要约"
- 定时任务扫描逾期订单，自动作废并把数量还回挂牌

```java
transition(order, CANCELLED, null, "system", "挂牌方未在期限内确认，摘牌自动失效");
//                        ↑ 不是任何真实用户干的，就签 system
```

**为什么签 `system` 而不是随便找个账号**：这条日志存在的意义就是将来定责，往里面写一个没做过这件事的人，是在唯一可信的记录里撒谎。

### 两个连带的护栏

**① 有待确认摘牌时不能撤牌。**

撤牌会释放整个冻结。如果此时有摘牌在等答复，那个订单就永远无法确认了。所以撤牌被拒绝：

```
有 1 笔摘牌等待您确认，请先确认或拒绝后再撤牌
```

**判断顺序有讲究**——先查待确认，再查"是否还开着"。因为一张被全部摘完的挂牌状态是 `FILLED`，不是 `OPEN`；如果先查后者，用户看到的是"该挂牌已关闭"，话说得没错，但没告诉他**下一步该做什么**。

**② 买方挂牌（`BUY`）不支持 `MANUAL`。**

`BUY` 挂牌背后没有预先冻结的货物，摘牌时才去找卖方库存。要"等确认"，就得保证确认时货还在——没人保证得了。所以数据库层面直接拒绝这个组合：

```sql
CHECK (confirm_mode = 'AUTO' OR side = 'SELL')
```

**约束写进数据库而不是只写在 Service 里**：Service 里的检查可以被人忘掉、被新代码绕开，约束不会。

## 二、订单状态机：转移表而不是 if-else

```java
private static final Map<String, Set<String>> TRANSITIONS = Map.of(
        PENDING_CONFIRM, Set.of(CONFIRMED, CANCELLED),
        CONFIRMED,       Set.of(CONTRACTED, CANCELLED),
        CONTRACTED,      Set.of(DELIVERING, CANCELLED),
        DELIVERING,      Set.of(COMPLETED),
        COMPLETED,       Set.of(),
        CANCELLED,       Set.of()
);
```

**为什么用表**：散落的 `if (status == ...)` 会让"合法的流转有哪些"只存在于作者脑子里，每加一个状态都是一次引入非法路径的机会。写成数据之后，只有一个地方要读、一个地方要测，**没列出来的流转就是不可能发生**。

**实测拦截**：

```
待确认 → 已完成                    ❌ 拒绝
待确认 → 已确认                    ✅
已确认 → 交收中                    ❌ 拒绝（必须先签约）
```

最后一条是关键：**不签约就不能开始交收**。状态机强制了这一点，而不是靠开发者记得检查。

### 但"谁能做这次流转"不是表能表达的

`PENDING_CONFIRM → CONFIRMED` 合法，但**只有挂牌方能按这个按钮**。买方按下去，等于替对方接受了自己的提议——那确认这一步就等于不存在。

所以状态机多了一个按调用者过滤的重载：

```java
public static Set<String> allowedFrom(String status, boolean callerIsLister) {
    if (PENDING_CONFIRM.equals(status) && !callerIsLister) {
        return Set.of(CANCELLED);   // 只剩"我不买了"
    }
    return allowedFrom(status);
}
```

它同时喂给两个地方：**服务端据此拒绝**，**接口返回的 `allowedActions` 也据此生成**。所以前端渲染出来的按钮就是服务端真的会接受的按钮——**按钮不是承诺，是事实**。

> **注意 `PENDING_CONFIRM` 只由 `MANUAL` 挂牌产生**。`AUTO` 挂牌摘牌即成交，直接进 `CONFIRMED`。一个永远没人问的"待确认"状态，比没有这个状态更糟。

### 每一次流转都留痕

```sql
t_order_status_log  -- 只增不改
```

状态列告诉你订单在哪，但**告诉不了你是怎么到这儿的、谁推的、有没有推过两次**。双方各执一词时，这条轨迹是唯一的证据。

### 踩到的坑：`updateById` 不会把字段写成 null

清空 `confirm_deadline` 时遇到一个很隐蔽的 bug：

```java
order.setConfirmDeadline(null);
orderMapper.updateById(order);   // ← 这一句什么也没干
```

MyBatis-Plus 默认的字段策略是 `NOT_NULL`——**生成的 UPDATE 语句会跳过所有 null 字段**。于是实体里是 null、接口返回的是 null，**数据库里还是旧值**。

这个 bug 最难的地方在于：**只看接口返回值的测试会全部通过**。它是在拿数据库里的行对照时才露出来的。

修法是给这一个字段单独开策略：

```java
@TableField(updateStrategy = FieldStrategy.ALWAYS)
private OffsetDateTime confirmDeadline;
```

**没有把全局默认改成 `ALWAYS`**：那样每个"只改一个字段"的更新都会把没填的列一并清空，把一个小坑换成一个更大的坑。**只给真的需要被清空的字段开口子。**

> 同一个类库里还有另一个同源的坑：`@TableLogic` 会让 `updateById` 忽略软删字段，所以"手工把 `deleted` 置 1 再 update"同样什么都没发生。**这一族的坑共用一个教训——ORM 的默认值策略会静默地改变你的意图，凡是想"清空/删除"的地方，都要用数据库里那一行去验证，而不是用返回值。**

## 三、合同：签署才让协议变成义务

### 快照，不是引用

合同里的数量、单价、金额是**从订单复制过来的**，不是外键关联。

```java
contract.setQuantity(order.getQuantity());
contract.setAmount(order.getAmount());   // 不是运行时计算
```

**为什么**：合同记录的是"双方在某一刻同意了什么"。如果订单后续被修正，合同不该跟着变——已经开出去的发票指的是这份文件，不是订单的当前状态。

### 数据库不允许"半边签字"

```sql
CONSTRAINT ck_contract_signed_complete CHECK (
    status <> 'SIGNED'
    OR (buyer_signed_at IS NOT NULL AND seller_signed_at IS NOT NULL))
```

**单方签字不是合同**。与其在代码里检查，不如让数据库根本存不下这个状态。

### 签署驱动订单流转

```java
if (bothSigned) {
    contract.setStatus(SIGNED);
    contractMapper.updateById(contract);
    advanceOrder(contract, user);       // 订单 → CONTRACTED
}
```

在**同一个事务**里完成，所以"订单已签约但没有合同"这种状态不存在。

## 四、资金：余额是流水的缓存

### 双写，缺一不可

每次资金变动都做两件事：**追加一条流水 + 更新账户余额**。

**流水是真相，余额是缓存。** 两者不一致时，流水是对的，余额是错的——这是一个对账问题，不是数据丢失。

### 冻结不是花掉

```java
account.setAvailableBalance(available.subtract(amount));
account.setFrozenBalance(frozen.add(amount));
// balance 不变
```

冻结只改变"可用 / 冻结"的分配，总额不动。这就是为什么订单取消能"退回"资金却**不构成一次退款**——钱从来没离开过账户。

### 支付从冻结里出，不从可用里出

```java
public void payFromMargin(...) {
    account.setFrozenBalance(frozen.subtract(amount));
    account.setBalance(balance.subtract(amount));    // 总额才真的减少
}
```

如果从可用里扣，同一笔订单可以被支付两次——因为冻结的钱还在那儿等着被再花一次。

### 流水不可变

```sql
-- 永不 UPDATE，永不 DELETE。错了就写一条冲正记录。
```

**能被修改的账本无法审计**。而在交易平台上，账本正是发生纠纷时用来定分止争的东西。

## 五、行情：为什么不是 K 线

### 数据形状决定图表形状

| | 期货 | 现货 |
|---|---|---|
| 成交频率 | 每分钟都有 | 冷门品种一天两三笔 |
| K 线 | 密集且有意义 | **几乎全空的格子** |

在这个数据上画蜡烛图，得到的是"三个孤立的柱子 + 大片空白"。

**正确的画法**：均价移动线 + 成交量柱 + **每个点的成交笔数**。

### 均价必须带着样本量

```java
points.add(new SeriesPoint(time, value, dayOrders.size(), volume));
```

**一笔成交算出的均价和四十笔算出的均价，在图上长得一模一样**——而"这个数字有多可信"的全部答案就在这里。所以每个点都带着笔数，悬停可见。

### 无成交的日子要断线

```java
// 无成交：value 为 null，而不是跳过这个点
points.add(new SeriesPoint(day, null, 0, BigDecimal.ZERO));
```

跳过的话，折线会从 gap 上直接拉过去，**暗示了从未发生过的交易**。

**附带踩到的坑**：项目全局配置了 `default-property-inclusion: non_null`，null 字段会被**整个省略**。这在前端是不可接受的——字段不存在和"值为空"是两回事，图表无法区分"无成交"和"无数据"。

```java
@JsonInclude(JsonInclude.Include.ALWAYS)
BigDecimal value,
```

### 没有用时序数据库

TimescaleDB 这类库在**tick 级数据**（每秒几千条、按索引扫一次都嫌贵）才划算。现货平台一天几笔成交，不是那个量级。

**给不存在的问题引入第二个数据库，本身就是一种错误。** 查询直接打在已经存着事实的表上，附带好处是**行情面板永远不可能和订单簿对不上**。

### SSE 而不是 WebSocket

行情是**单向**的：服务器有消息，客户端听。SSE 是普通 HTTP，自动重连，不需要协议升级，也不需要网关特殊配置。

WebSocket 会带来握手、心跳、重连策略和网关配置——为了买一条这个功能根本用不上的客户端→服务器通道。

**代价**：`EventSource` 无法设置请求头，所以流端点额外接受 query 参数传 token。这是真实取舍（URL 里的 token 会进访问日志），限于单一路径，代码里明确写了，没有假装不存在。

## 六、RAG：混合检索，按 RRF 融合

### 嵌入模型是唯一非 Anthropic 的环节

**Claude 不提供 embedding 接口。** 所以向量化用的是本地 BGE-M3（Ollama 部署）：中文效果好、零调用成本、离线可跑。

接口只有"文本进、向量出"两个动作，换托管 API 只改一个类。

### 为什么必须混合

| 检索方式 | 擅长 | 盲区 |
|---|---|---|
| 向量 | 同义改写（"履约担保金" ≈ "保证金"） | 精确术语反而不稳 |
| 关键词 | 精确术语（"溢短装"、"清算通"） | 换个说法就找不到 |

**两种都做，按 RRF（倒数排名融合）合并**：

```
score = Σ 1 / (k + rank)     k = 60
```

**为什么不用加权求和**：余弦相似度和 trigram 相似度**不是可比的数字**，给它们分配权重就是拍脑袋。RRF 只用排名，不需要在两套刻度之间做校准。

### 两个靠实际运行才发现的问题

**① `similarity()` 用错了**

```sql
-- 错的：短查询对长文本，整句相似度必然很低
WHERE c.content % #{query}          -- % 要求相似度 > 0.3

-- 对的：问"查询是否是文本的一部分"
ORDER BY word_similarity(#{query}, c.content) DESC
```

五个字的问题对两百字的段落，无论匹配得多好，整句相似度都很低——而这个方法存在的意义恰恰是服务这类查询。结果就是**返回 0 条**。

**② 阈值过滤会静默返回空**

不给 WHERE 加阈值，直接排序取 Top N。因为**调用方无法区分"没有匹配"和"阈值设高了"**——两种情况的返回值一模一样。排序取前 N 至少总是返回可用的候选，让融合阶段决定谁最终胜出。

### 引用出处是可验证性的前提

工具返回的每段都带着文档编号和标题，系统提示要求引用：

```
[1] 出处：交收管理办法（RULE-DELIVERY）
结算重量以实际过磅重量为准，而非合同约定重量……
```

**没有出处的规则回答无法验证**——用户分不清自己拿到的是平台真实的规则，还是一个听起来很合理的编造。

## 七、这一段的面试考点

1. **"为什么没有撮合引擎？"**
   → 现货的法律形态是一对一的合同订立，挂牌=要约、摘牌=承诺。集中竞价是期货市场的特征。

2. **"订单状态怎么管理的？"**
   → 显式转移表，不是散落的 if-else。没列出的流转不可能发生。
   → 追问"谁能做这次流转" → 表只表达合法性，不表达权限。加一个按调用者过滤的重载，同时喂给服务端校验和接口的 `allowedActions`。
   → 追问并发 → 乐观锁 + 状态校验。

2b. **"为什么有两种成交模式？"**
   → 挂牌交易里，"发布挂牌"到底算不算挂牌方已经同意，市场上两种做法都有。做 `AUTO`（挂牌=要约，摘牌即承诺）还是做 `MANUAL`（挂牌=要约邀请，需确认），决定了**货权在哪一刻转移**——这是不能含糊的一件事。
   → 加分：说明这是**要约本身的属性**，所以存在 `t_listing` 上而不是当全局开关。
   → 加分：说明 `MANUAL` 摘牌时**不能转移货权**，否则确认就是摆设；同时也不能什么都不做，否则两个买家会摘走同一批货——正确做法是只减挂牌剩余量，冻结不动。

3. **"数量/金额怎么存的？"**
   → `NUMERIC`，Java 侧 `BigDecimal`。绝不用浮点。
   → 追问"为什么" → 二进制浮点误差在金额上是事故。

4. **"并发扣减怎么防超卖？"**
   → 乐观锁 `WHERE id = ? AND version = ?`，失败拿到零行结果并提示重试。
   → 加分：说明为什么不用悲观锁（锁持有时间长，且这里是短事务）。

5. **"余额和流水的关系？"**
   → 余额是流水的缓存聚合，流水是真相。不一致时以流水为准，这是一个对账问题。

6. **"行情为什么不是 K 线？"**
   → 现货成交稀疏，K 线大部分是空的。用均价线 + 成交量 + 每个点的成交笔数。

7. **"RAG 为什么用混合检索？"**
   → 向量管同义、关键词管精确，各有盲区。RRF 融合不需要校准两套不可比的分数。

8. **"AI 怎么防止越权查别家数据？"**
