# SpotLink 实施计划

制定日期：2026-10-08。本文定义实施要求，当前进度以 14.9 的真实执行记录为准。要求为：前端可选择 Spring AI 或 LangChain 两套独立顾问，Agent/知识库/RAG 为主线；完整数据由容器生成并导入；生成和实际业务数据不纳入 Git；本地依赖统一 Docker 管理；Codex 按明确路径、命令和验收连续执行。

本文为唯一实施计划，已合并早先的 AI 完善计划。全部任务、规范、数据、脚本、设计、业务优化和验收要求均在本文；代码审查报告仅作为问题证据，不承担另一份实施计划。目录树中的开发文档、数据 README 和评测报告是未来交付时的使用说明与结果记录，不是本轮分散的计划文件。

**给 Codex 的阅读入口：**先读第一节的边界、第三节的提交规则、第十二节的 C00–C74 顺序，再按[第十四节执行协议](#十四codex-阅读与命令执行协议)选择当前任务。文件范围、检查模式、命令、失败分支和恢复规则统一在该节定义；业务依据查第八节，数据查第九节，双引擎/Agent/RAG/个人模型隐私查第十节。本文中的未来脚本是待实现的接口约定，执行前必须检查是否已由前置任务创建，不可把计划示例当作现成命令。

## 一、目标与实施边界

在独立目录建设现货通，形成以 AI 顾问为核心的 AI 应用学习项目。实现 Java/Spring AI 与 Python/LangChain 两套真实引擎，前端可选择。重点是模型接入、会话记忆、工具调用、Agent 编排、知识库处理、RAG 和效果评测，并在相同数据/权限/问题上比较两种框架；交易业务提供可验证的数据与工具场景。

实施时尽早跑通“克隆 → 导入合成数据 → 启动 → 顾问回答并展示依据”的最小闭环，再逐步增加工具、多步 Agent 和混合检索。不能先重做完整交易平台，最后才接一个聊天窗口。所有演示案例绑定数据集、身份、问题、工具或知识来源及预期结果。

建议新目录：`D:\Project\spotlink-next`。项目展示名称仍为“现货通 SpotLink”；文件夹名称用于区分新旧版本。实施时若目标目录已存在，先检查内容，不覆盖已有文件。

命名统一：产品名称“现货通 SpotLink”，目录/Compose 前缀 spotlink-next，计划《SpotLink实施计划》；页面、README、文件名、仓库和镜像/容器名称均使用这些产品名或职责名，不加入过程性名称。

- 原目录 `D:\Project\spotlink` 保留作为参考，不移动、不重置、不改写历史，也不让新项目使用它的数据库和 Docker 数据卷。
- 新目录建立独立 Git 仓库，从目录与配置骨架开始，按完成并验证的功能逐步形成历史；不把旧项目全部复制后作为一个“完成建设”的提交。
- 旧项目作为设计与实现参考，复用代码须先确认职责、规则、依赖和测试，再按模块纳入；不复制旧 `.git`、运行配置、密钥、IDE 配置、node_modules、target、dist 和运行数据。
- 默认只做本地提交、标签和备份；不自动推送、创建远程仓库、上线或迁移真实数据。
- 提交作者和提交者使用用户现有 Git 身份；不附加 AI 作者、机器人身份、AI 联合作者或工具签名。
- 代码注释、提交说明、页面文案、README 和使用文档以中文为主。技术名称、标识符、协议名、命令和环境变量保留标准写法。
- 业务范围包括：身份与企业、角色权限、品类仓库、电子库存、挂牌与订单、合同和交收、模拟资金、行情和待办、知识库、AI 顾问、运营后台。暂不增加真实银行、发票、物流对接等外部系统。
- 项目代码与数据分开管理：backend/frontend 保存源码；data 保存数据定义、生成器、导入模板和人工维护的知识源；生成后的业务数据集、实体记录、散列清单、渲染 SQL、测试输出等全部放被忽略的 .local/data 或 Docker 数据卷，不纳入 Git。GitHub 克隆后由容器自动生成、校验并导入，不依赖额外私有仓库或个人机器文件。
- 真实业务/生产数据、模型会话与向量、数据库导出和任何运行数据不做 Git 版本控制。无关文件、缓存、诊断草稿和重复记录不提交；版本控制仅保留重建功能所必需的代码、配置模板、规则、脚本与使用说明。
- 本地项目依赖统一 Docker 管理：Java/Maven、Node/npm、Python、数据库、缓存、Ollama 以及测试/浏览器工具都在对应容器中使用；宿主机只承担 Git、Docker、PowerShell 脚本入口与浏览器访问，不安装项目运行时或依赖包。

建议技术路线：Java 21、Spring Boot 模块化业务后端及 Spring AI 顾问；Python、FastAPI 和 LangChain 构成独立顾问服务；MyBatis-Plus、MySQL 8.4、Redis、Ollama/BGE-M3；前端 React、TypeScript、Vite、React Query、Ant Design 与 ECharts。保留成熟基础组件，重新设计页面布局、交互和视觉。Maven Wrapper、npm/Python 锁文件与经验证的容器运行时固定环境；框架版本升级单独验证和提交。

## 三、本地版本控制规则

### 3.1 仓库与身份

1. 在新目录初始化 `main` 分支，使用仓库级配置固定用户现有姓名与邮箱；不改变全局 Git 配置。
2. 第一次提交前核对有效的 Author/Committer 身份，防止环境变量或其他工具覆盖。若实际身份缺失或明显为机器人，再向用户核实，不自行编造姓名或邮箱。
3. 不添加 `Co-authored-by`、`Generated-by`、工具推广文字或 AI 署名；不修改旧仓库的历史作者。
4. 提交时间使用实际完成时间，不伪造早期日期，不把多日工作集中伪装成从零过程。
5. 每个功能保持可构建、可验证的状态；需要拆成多个独立子功能时，分别完成、验证和提交。

### 3.2 每次功能提交的时间点

执行顺序固定为：

```text
明确本次功能与验收条件
    → 实现功能、针对性测试及相关文档
    → 运行对应测试和必要的联调
    → 检查代码差异、暂存范围、密钥与临时文件
    → 立即做一个中文提交
    → 用 git log / git status 核对提交与工作区
    → 开始下一个功能
```

- 不等到整个阶段或所有页面做完才提交。
- 测试失败时先修复，不将失败功能标成完成提交。测试驱动开发中的临时失败可以发生在工作区，但功能完成提交必须通过对应检查。
- 后端改动检查相关单元/集成测试；前端改动检查类型、lint、组件或交互测试及构建；跨端功能检查实际接口与页面。
- UI 和图片改动进行实际渲染与视觉检查；纯规范或文档变更检查内容和链接，不为形式上的“有测试”添加无意义用例。
- 真实 AI 评测单独显式运行；普通提交检查不默认产生模型调用费用。

### 3.3 中文提交格式

标题统一为：`类型（范围）：动作与结果`。标题建议不超过 60 个中文字符。

类型使用：初始化、规范、部署、设计、资源、功能、修复、整理、测试、文档、性能。

示例：

```text
功能（库存）：实现企业库存登记与数量校验

改动：新增库存登记接口和页面，保存品类、仓库、单位及商品规格。
验证：登记、非法精度、跨企业操作和数据库数量约束测试通过。
影响：新增库存表迁移，既有业务规则未变化。
```

```text
修复（订单）：并发取消失败时回滚库存与状态日志

改动：检查订单版本更新结果，冲突时中止取消事务。
验证：取消与发货并发测试通过，没有新增退货库存或虚假状态日志。
影响：发生并发冲突时返回明确的重试提示。
```

要求：描述实际完成的行为；不写“完善全部功能”“全面优化”等无具体对象的标题；验证内容必须实际运行，不填写未执行命令或虚构通过数量。

提交前检查脚本负责格式、暂存文件和有效身份核对；完整功能验证由检查脚本和功能验收记录共同支持，不依赖一份写着“通过”的提交正文。

### 3.4 里程碑、记录和回退

- 建议标签：`v0.1.0` 基础环境、`v0.2.0` 数据与顾问最小闭环、`v0.3.0` 新 UI 与可信业务、`v0.4.0` 完整数据/Agent/RAG、`v1.0.0` 本地演示验收版。标签只在对应检查通过后建立。
- 功能验收记录使用功能编号关联提交，Git SHA 以历史为准；不为提前写入本次提交自身 SHA 制造额外的无意义提交。
- 用新的修复或 revert 提交回退已记录工作，保留历史，不随意强制重置。
- 数据库回退单独考虑：代码标签不等于数据可回退。破坏性迁移前备份，恢复时对齐 schema 与应用版本。
- 阶段完成后可生成本地 Git bundle 备份到被忽略的 `.local/backups/`；Git bundle 不包含未跟踪配置、数据库和未提交文件，另外备份必要运行数据。

### 3.5 Git 纳入与排除规则

| 分类 | 是否提交 | 范围 |
|---|---|---|
| 功能源码与测试 | 是 | backend/frontend、必要测试断言、脚本与迁移 |
| 工程与依赖定义 | 是 | Dockerfile、Compose、Wrapper、依赖声明/锁文件、配置模板、格式规则 |
| 数据重建依据 | 是 | schema、seed/规模配置、场景定义、生成器、参数化插入模板、人工维护的预期断言和知识源 |
| 正式产品资源 | 是 | 页面实际引用的压缩图片/图标、必要来源说明；只保留产品所需版本 |
| 必要使用与验收说明 | 是 | 中文 README、本文、规则/架构/操作说明、精简结果摘要；不放逐次流水或重复文件 |
| 生成的数据集与 SQL | 否 | 生成的 JSON/JSONL/CSV、实体行、已渲染 INSERT、生成期望值/散列清单/覆盖报告 |
| 真实数据及数据库内容 | 否 | 生产/演示数据库、数据库导出、备份、业务操作结果、会话、工具轨迹和向量索引 |
| 工具运行产物 | 否 | node_modules、Maven/npm/pip 缓存、target/dist、coverage、日志、截图、录屏、逐次评测 JSON |
| 无关或临时内容 | 否 | IDE 个人设置、图片候选/母图、工具响应、调试文件、临时提交正文及操作流水 |

对“生成数据不控制”的处理统一为：保存如何生成和如何检验的定义，不保存生成结果。数据版本标记的是生成规则/schema 的兼容版本；每次运行的文件散列与导入批次记录放 .local 和数据库台账。功能提交可以修改生成规则并重新生成测试，但只能暂存规则、代码和必要说明。

拟定 .gitignore 的基础内容如下；实际按工具产物补充，并用 git check-ignore 核验，不能因为已有文件被跟踪就以为新增忽略规则能自动移除它：

~~~gitignore
.local/
.env
.env.*
!.env.example
!.env.*.example
**/node_modules/
**/target/
**/dist/
**/coverage/
**/.venv/
**/__pycache__/
**/.pytest_cache/
**/test-results/
**/playwright-report/
*.log
*.dump
.idea/
.vscode/
Thumbs.db
.DS_Store
~~~

不要全局忽略所有 SQL/JSON/图片：结构迁移、配置模板、场景规则和正式 UI 素材仍是必要输入。生成器固定只向 .local 或数据卷写输出，提交前检查工作区与暂存清单，对误入源码目录的运行数据直接报错；不能通过 git add -f 绕过。文件若已误提交，核对归属后停止跟踪并另做修正，不擅自重写历史。

## 五、UI 重设计方案

### 5.1 产品定位与视觉方向

定位为“面向企业采购与销售人员的中文现货工作台”，以 AI 顾问、业务操作和可核对的数据为中心。

初步方向：浅灰或暖白背景、深色文字、克制的深蓝主色、语义明确的状态色；中文无衬线字体，数字对齐；明确边界、适量留白、适合表格阅读。正式色值由设计变量和对比度验证确定。

- 桌面工作台：侧边导航、顶部企业与账号信息、主内容区。
- 访客入口：独立首页和公开行情/规则，清楚区分登录后的企业功能。
- AI 顾问作为核心入口：Spring AI/LangChain 选择器、会话导航、问答内容、工具与引用展开区；每轮和会话显示实际引擎，状态反馈与正文分开；工作台和业务详情提供带权限的“向顾问提问”入口。
- 提供分组示例问题和场景说明，关联导入后的真实合成记录，点击后发起实际问答，不以预置答案冒充模型输出。
- 页面信息围绕“当前状态、需要我做什么、数据依据”组织，不堆叠装饰性统计卡片。
- 公共首页可使用商品或仓储场景图片；密集业务表格与顾问答案不铺大背景图。
- 使用一种基础组件库和图标体系；重设主题、布局、表格、表单、详情、弹窗、按钮和状态规范。

### 5.2 页面清单与交互要求

| 页面 | 设计重点 |
|---|---|
| 首页与登录 | 简明产品介绍、真实能力、明确入口；登录失败有具体原因 |
| 工作台 | 待我处理、等待对方、最近业务及顾问入口；区分待办与可取消动作 |
| 库存 | 数量三口径、单位、仓库、规格和预留明细；表单按品类展示规格 |
| 交易大厅 | 买卖方向、商品属性、剩余数量、价格与成交模式；操作前清楚展示条件 |
| 订单与合同 | 双方责任、时间线、可执行动作、签署状态、取消申请与交收信息 |
| 行情 | 成交口径、时间范围、样本量、单位和真实连接状态 |
| AI 顾问 | 问答、引用、工具、耗时、错误和降级；不把模型推理草稿展示成最终答案 |
| 规则与知识维护 | 公开规则可读；维护入口按权限显示，重算向量显示真实进度与结果 |
| 企业与模拟资金 | 企业信息、成员权限、账户和模拟操作边界 |
| 运营后台 | 审核、冻结、用户状态、角色、订单查询和审计；菜单与后端权限一致 |

每页完成时检查加载、空数据、失败、无权限、成功反馈和键盘操作。桌面检查 1440/1280/1024，窄屏检查 768/390；表格可在自身容器滚动，不让整个页面横向溢出。正文对比度至少 4.5:1，状态同时有文字或图标。动效主要用于状态反馈，支持减少动态效果。

### 5.3 设计实施步骤

1. 先形成导航、页面结构和关键流程原型，优先工作台、顾问、库存、交易与订单详情。
2. 确定设计变量：颜色、字体、字号、行高、间距、圆角、边界、表格密度与状态。
3. 制作可实际打开的静态页面验证布局，必要时用生成图片辅助视觉探索；界面文字和控件由代码呈现。
4. 接真实接口，逐页验证业务行为，不将静态 mock 数据当成完成页面。
5. 每页制作与测试完成即提交；最终统一检查导航、视觉、状态文案和响应式表现。

## 六、gpt-image 图片与资源管理

图片生产可以使用已安装的 gpt-image 技能。图片生成与服务供应商配置分开，不把图片 API Key 或技能私有配置复制到项目。

拟生成资源：1 张首页场景主图、1 张登录辅助图、少量商品或仓储示意图，以及确有需要的空状态插图。先确认图片在界面中的具体尺寸与作用，再生成；不为了展示生成能力给每页加图。

流程：

```text
确定用途与构图
    → 编写提示词与尺寸要求
    → gpt-image 生成候选
    → 检查内容、质量、留白与裁切
    → 选择素材并保存原始文件
    → 转换 WebP/AVIF 等适用格式并压缩
    → 页面中实际验证
    → 登记素材并提交
```

要求：

- 技术规格以实际图片端点支持为准；不在计划中宣称某模型已可用或某尺寸一定支持。
- 图片内避免关键中文文字、数据、按钮和品牌标志；界面文字由前端准确排版。
- 生成场景作为示意图，不声称为平台真实仓库、真实客户或真实货物证明。
- 素材采用稳定用途名，例如 `home-warehouse-hero.webp`；不采用随机输出文件名。
- manifest 记录用途、来源类型、模型、生成日期、提示词位置、原始及衍生文件、尺寸和散列；不记录密钥或带临时鉴权的地址。
- 图片最终本地存储，不依赖临时生成 URL；固定宽高、合适的替代文本，按位置决定延迟加载。
- 初始资源预算：首屏主图优先控制在约 300 KB 内，其他图尽量低于 150 KB；以实际清晰度和网络测试调整，不强行压坏图片。
- 只有页面实际引用的压缩成品、必要提示词与精简来源说明纳入 Git；母图、未采用候选和完整 API 响应全部存入 .local，不提交试稿或无关生成产物。
- 图片生成只在素材任务执行，不绑定一键启动，不让普通测试产生图片调用费用。

## 七、Docker 管理与一键启动

### 7.1 默认运行方式

建议默认全容器启动：MySQL、Redis、Java 后端/Spring AI、Python LangChain 顾问服务、前端静态服务；Ollama 为可选 profile。首次体验仅需 Git、Docker Desktop、Windows PowerShell，不要求本机另外安装 Java、Maven、Node 或 Python。

开发模式使用 `compose.dev.yml` 显式启用前端热更新及相应后端开发方式，工具链全部在容器中运行；通过源码挂载、调试端口和浏览器进行开发，不增加需要本机 Java/Node/Python 的另一套安装流程。数据生成、导入、构建、评测及浏览器测试使用 compose.tools.yml 的一次性工具服务，隔离集成环境由 compose.test.yml 管理。

| 项目 | 约定 |
|---|---|
| Compose 项目名 | `spotlink-next` |
| 默认前端地址 | `http://localhost:18080` |
| 默认后端诊断地址 | `http://localhost:18081` |
| 开发前端地址 | `http://localhost:15173` |
| 数据库、Redis | 默认仅容器内部可达；调试时可显式映射到 14306/17379 |
| 对宿主机绑定 | 默认 `127.0.0.1`，不无意开放整个局域网 |
| 数据卷、网络 | 由新 Compose 项目独立命名，不复用旧项目名称或固定旧容器名 |
| 模型服务 | 对话模型外部配置；Ollama 可选，缺少时按说明降级 |

端口可配置，实际采用前先检查占用；成功提示使用最终生效端口。容器之间使用服务名通信，容器内部不得把 localhost 当作另一服务地址。

### 7.2 容器与配置要求

- 前后端多阶段构建，固定经过验证的基础镜像版本；生产运行阶段尽量以非 root 用户运行。
- `npm ci`、Maven Wrapper 与锁文件保证依赖可重复安装；修复已知构建依赖漏洞后验证，不自动升级全部主版本。
- Maven/npm/pip 安装、编译和测试在工具容器中执行；缓存和 node_modules 使用独立命名卷，不在宿主机安装项目包，不把宿主机 node_modules 带进镜像。Python 工具的版本与依赖同样锁定。
- 浏览器测试与截图工具在包含对应浏览器版本的容器中运行；宿主浏览器只用于用户查看页面。采用远程浏览器连接时明确端点与版本，不要求在宿主机安装 Playwright 浏览器依赖。
- 工具服务按职责命名为 backend-tools、frontend-tools、data-tools、evaluation-tools、browser-tests；通过一次性 run --rm 执行，全部复用明确的镜像/依赖定义，不给每个任务造一套运行时。
- LangChain 运行服务命名 advisor-langchain，测试/依赖工具命名 langchain-tools，Python 依赖锁定后在镜像内安装；服务默认仅内部网络可达，由 Java 顾问网关调用。两引擎通过统一模型配置与受限代理使用后端默认/用户个人模型，各自健康与适配能力分别报告，一套服务失败不阻止另一套或业务平台启动。
- MySQL/Redis、依赖缓存和可选 Ollama 模型分别使用本项目命名卷；测试使用独立项目名/网络/卷，避免测试清理波及演示环境。Docker 镜像、缓存和卷不进入 Git，定义与锁文件才进入 Git。
- `.dockerignore` 排除 .git、.env、构建输出、日志、备份和图片草稿，密钥不进入镜像层。
- MySQL 和 Redis 有健康检查；后端有基础就绪状态，前端验证静态页面及反向代理。启动顺序包含“健康可用”，不能只依据容器已启动。
- 日志设滚动和容量上限；开发与默认运行的重启策略分别说明，避免手动停止后被莫名拉起。
- 首次启动生成本机配置与随机数据库/Redis 密码、JWT 密钥；模板不含真实密钥。配置生成幂等，后续启动不重写密码。
- 个人模型凭证的加密主密钥单独生成/注入，持久保存在 .local/secrets 的受保护文件或外部 secret，再只读挂入需用容器。数据库已有密文而主密钥缺失时显示需要恢复，不静默生成新 Key 让既有配置无法解密。数据库与密钥分别备份并记录恢复步骤；均不进 Git。
- 默认配置不包含模型 Key。顾问未配置不影响核心平台启动，但必须准确显示未配置状态。
- 默认懒人入口使用明确标注的本地演示模式，首次启动自动调用独立导入脚本，导入完整 demo 数据包并验证；正式或空数据模式不自动导入。演示账号及其密码策略在中文数据说明中列明，非演示环境关闭初始化。
- 应用正常启动不隐式创建演示业务数据。脚本通过独立导入作业执行；schema、业务文本与知识向量分别记录结果。没有真实 Embedding 服务时不写假向量，不把关键词可用描述成完整 RAG 已就绪。
- 时间统一约定 Asia/Shanghai，覆盖应用、JDBC、数据库会话和脚本；做写入与读取往返测试。
- 单独的新数据库可以建立整理后的迁移基线，后续按功能新增版本。不得让该基线连接旧数据库；已执行的新仓库迁移也不能事后改写。

### 7.3 一键启动流程

`start.cmd` 调用 `scripts/start.ps1`，处理带空格和中文的路径，从脚本所在目录解析项目根。若 Windows 执行策略阻止脚本，入口采用仅当前进程适用的调用方式，不修改系统级策略，不要求管理员权限。

启动过程：

1. 检查 Docker 命令、Compose 版本和 Docker 引擎是否可用。
2. 检查项目路径、配置、实际需要的端口及存储条件。
3. 首次创建本机 .env；缺模型 Key 明确提示，日志不打印敏感值。
4. 构建或复用镜像，区分首次构建、增量构建和已在运行状态。
5. 等待 MySQL/Redis 健康，使用迁移工具作业准备 schema。
6. 首次本地演示启动调用 prepare-dataset/import-data：在 data-tools 中按规则生成并校验 .local/data 数据，再导入业务及知识文本。已有成功台账则核验版本后跳过，不重新生成覆盖已操作数据。
7. 启动后端/前端并检查就绪、HTTP 页面与 `/api` 代理；模型调用及大模型下载单独显式启用。
8. 输出有效地址、运行模式、顾问/检索状态和停止、日志命令。

```text

[2/8] 检查配置与端口：通过

LangChain 顾问：服务已就绪，未配置模型密钥，当前不可用
知识检索：关键词检索可用；向量检索未启用
查看日志：scripts\logs.ps1
停止服务：stop.cmd
```

上面是拟定格式。实现时依据实际探测填写，不将“配置存在”写成“模型已连通”，也不将镜像构建完成写成服务就绪。

错误示例：

```text
[失败] 后端在等待期限内未就绪。
阶段：数据库迁移
原因：检测到迁移校验失败。
日志：scripts\logs.ps1 -Service backend
处理：检查迁移版本和当前数据库；不要直接重置数据。
```

错误原因必须来自实际日志或检查；未知时显示“原因未确定”，不猜测。超时有上限，返回非零退出码；双击入口失败时保留窗口供阅读，自动化参数可关闭等待。

### 7.4 生命周期与数据维护

| 操作 | 脚本行为 |
|---|---|
| start | 幂等启动当前项目，已健康时报告已在运行，不重复拉起实例 |
| stop | 仅停止/移除当前项目服务，保留数据卷 |
| restart | 重启指定服务或本项目，不影响旧项目与其他容器 |
| status / logs | 显示本项目状态和指定服务日志，隐藏敏感配置 |
| check | 按模式运行离线测试、集成测试、前端检查和基础联调 |
| setup-demo | 首次环境准备、迁移、数据导入、校验及前后端启动；逐步显示状态 |
| import-data | 导入选定合成数据包；空演示库可自动导入，非空冲突库停止并解释，不覆盖真实数据 |
| data-status | 显示数据版本、步骤、行数及知识/向量状态，并给出可重试命令 |
| backup / restore | 明确项目、数据库、版本及备份位置，验证备份和恢复结果 |
| reset-data | 明确提示会删除哪些新项目数据，默认要求输入确认；执行前检查范围并备份 |

禁止自动运行全局 Docker prune、全局 volume prune 或无范围的删库。重置和恢复操作只作用于核验过的新项目资源，不把日常 stop 实现成删除数据卷。

启动脚本验收必须覆盖：首次启动、重复启动、已有镜像启动、端口被占用、Docker 未开启、构建失败、迁移失败、缺模型 Key、向量服务不可用、停止后数据保留、中文/空格路径，以及两个项目同时存在时的隔离。

数据首次导入、分步骤命令、重复执行与中断恢复的完整规则见第九节；启动和数据脚本共用底层实现，不维护两套互相不一致的导入逻辑。

## 八、业务规则与已识别问题的优化方案

### 8.1 核心口径先统一

新项目将业务规则写入 `docs/业务规则.md`，后端状态校验、接口动作、前端按钮和知识语料共同以该口径为准。

- 保留卖方 AUTO/MANUAL 两种挂牌；买方挂牌先限定 AUTO。
- 挂牌未摘数量与待确认订单数量分别管理预留。MANUAL 摘牌先将相应预留归属转到订单，确认后才执行货权登记；撤牌仅释放尚未被订单占用的部分。
- 明确库存来源、目标和业务关联。每次过户同时扣卖方并增买方；反向操作引用原过户记录，不能只凭冻结 ID 猜测是否成交。
- 建议买方成交库存在完成交收前处于受限状态，完成后才可再次挂牌，降低取消与再次转售冲突；货权登记和物理交收分别表达。
- 待确认订单可由请求方撤销、挂牌方拒绝或系统超期失效。已成交/已签署订单建议采用双方确认的取消申请；交收中和已完成不允许直接取消。申请单独记录，不任意扩张主订单状态。
- 已成交取消通过后，检查相关货物仍可恢复，在同一事务逆转来源与目标库存、预留、状态和日志；存在无法恢复的业务占用时明确拒绝。
- 默认金额由规范化数量和单价计算并固化，数量最多 3 位、单价及金额最多 4 位，统一校验上限和舍入规则。
- 卖方挂牌的单位、仓库和规格由可信库存继承；买方摘牌显式选择匹配源库存，不能只按品类随便挑货。
- 模拟资金保持独立且可验证的账户/流水功能；当前是否与订单支付联动必须如实说明。未实现支付联动时，订单完成不宣称发生资金划转。

### 8.2 对照整改

| 审查问题 | 新项目实施方案 | 必须验证的场景 |
|---|---|---|
| F01/F02：取消货权错误 | 过户关联、受限买方库存与原子逆转 | SELL 全额/部分、BUY、重复取消、不能恢复时拒绝 |
| F03：并发签署卡单 | 合同版本锁或明确行锁；双方签名与订单推进原子完成 | 双方同时签、单方重试、签署与取消冲突 |
| F04：忽略订单 CAS | 所有版本更新检查行数；失败回滚副作用 | 取消/发货、重复取消、确认/超期竞争 |
| F05：数量与金额舍入 | 请求和服务精度约束，统一金额计算 | 0.0015 被拒绝、合法边界、上限、总量守恒 |
| F06/F07/F15：鉴权与撤销 | 企业有效状态、令牌用途、授权缓存失效与版本校验 | 冻结后的旧 token、refresh 作为 Bearer、并发权限回填 |
| F08/F21：前端串数据 | 查询键包含身份；账号切换取消请求并清缓存；会话响应归属检查 | 同浏览器换企业、A/B 会话乱序 |
| F09/F19/F20：物理属性与规格 | 可信源库存快照、schema 表单与未知键保留 | kg/吨、跨仓、中文键、非铜规格、接口返回一致 |
| F10：逾期仍成交 | 请求直接检查时间，扫描只是清理；原子争用订单状态 | 截止前后、扫描并发、合法预留回收 |
| F11：空关联报错 | DTO 统一可空策略，批量装配空键安全 | 单条/全批无仓库、关联缺失、发布成功响应 |
| F12/F13：行情口径错误 | 排除待确认和取消；按成交时间计算；图名匹配指标 | 最新交易、品类过滤、超过读取上限、不同单位 |
| F14：审计无独立提交 | 提交后以独立事务写审计，明确失败补偿与日志 | 成功有审计、回滚无成功审计、审计失败不回滚业务 |
| F17：修复脚本危险 | 由有范围、可预览、原子的维护任务替代 | 不释放有效待确认预留、中断重试、备份恢复 |
| F18/F24：表单与详情失配 | 强类型表单订阅、按 ID 查询详情、事件失效关联缓存 | BUY 定价、面议切换、对方签署后详情更新 |
| F22/F23：通知与刷新 | 提交后通知；真实连接状态；准确刷新行情/合同/轨迹 | 回滚不通知、第三方行情更新、重连后校准 |
| F16/F25：AI 与知识偏差 | 保留调用依据；知识内容与现行业务规则同版本 | 无答案重试、规则更新、未实现流程不误报 |

行情优先提供真实成交价/成交量、当前库存与在挂量。“每日历史在库余额”只有保存相应事件或快照后才提供；若展示新登记量或新发布量，则明确使用对应名称，不将当前数据按创建日分组冒充历史余额。

## 九、合成数据集、覆盖与首次导入

### 9.1 代码、数据集与运行数据分离

数据交付包含完整生成规则、生成器和导入模板，生成后的业务数据不纳入 Git。GitHub 克隆者执行懒人脚本，由固定版本的 Docker 工具容器按 demo 配置生成标准数据集、渲染插入文件并导入，无需找作者索要数据库、安装本机 Python 或调用模型生成业务数据。数据“完整”指全部类型/状态/流程可由规则重现，不要求将生成的实体记录提交到仓库。

四类内容分开管理：

| 内容 | 位置与职责 |
|---|---|
| 应用代码和结构迁移 | backend/frontend；db/migration 负责结构及必要系统元数据 |
| 数据重建依据 | data；含生成配置、场景定义、参数化插入模板、人工知识源、覆盖要求与断言 |
| 导入与维护实现 | scripts/data 与独立 Java 导入作业；复用项目类型/校验能力，但不在业务启动中隐式灌数据 |
| 生成数据与实际运行 | .local/data 保存 JSON/JSONL、渲染 SQL、运行 manifest/期望/报告；数据库与向量在 Docker 卷，日志在 .local/logs；全部不进入 Git |

代码与数据重建依据在同一仓库的独立目录，一次克隆获得全部必要输入；全部实际数据在容器内生成后另存 .local 或数据卷。数据规则版本独立编号，通过版本模板声明兼容应用/schema，运行 manifest 记录本次实际文件散列和行数；不能只靠文件名猜兼容性。

### 9.2 数据包与生成规则

| 数据包 | 用途与要求 |
|---|---|
| minimal | 生成早期最小顾问闭环所需的企业/权限/库存/规则；不是最终完整演示包 |
| demo | 最终默认首次生成与导入，覆盖全部合法类型/状态及可操作流程，规模适合本机 |
| acceptance | 在隔离测试环境生成边界、冲突、跨企业和知识攻击场景，不混入日常演示库 |
| performance | 可选分页/检索规模测试；只提交参数与生成器，结果不入 Git |

生成器使用固定 seed、稳定业务编号和显式小数精度，向 .local/data/<规则版本>/<批次>/ 输出数据、渲染 SQL 与期望值。运行 manifest 同目录保存数据规则版本、生成器版本、seed、时间规则、兼容迁移、文件 SHA-256、各阶段行数和依赖；manifest 模板/结构定义才进入 Git。合成企业/联系人使用虚构名称及非真实联系方式，密码由项目实际编码器生成散列；示例密码仅用于本地演示。

时间分两种：回归包采用固定时钟；演示包使用一个首次准备时固定的 baseTime，按相对偏移渲染截止日、成交日和行情日期。准备结果与时间锚保存在本次导入批次中，重试沿用原值；重复导入不延长旧挂牌，不改写已操作数据。静态历史案例与可继续操作的案例分组，防止首次导入后所有挂牌立即过期。

业务场景使用隔离的 scenarioId/业务编号与稳定身份，关联数据在同一场景内自洽。库存来源/目标、预留、货权、合同、状态日志和模拟流水由统一场景生成，不靠随意填几个枚举值拼出不可能状态。数据初始化不向在线用户广播业务通知、不发外部消息、不调用模型伪造历史回答。

### 9.3 “每一种类型”的覆盖矩阵

以建设后的实际枚举、SQL 约束、商品 schema、角色权限和状态转换表为基准，生成覆盖清单；每新增一种类型或转换，必须在对应功能提交中同步补场景。类型覆盖、状态覆盖、合法转换覆盖和边界/拒绝覆盖分别统计，不以几张有数据的截图宣称全部覆盖。

| 维度 | 必须覆盖的数据/测试 |
|---|---|
| 企业与身份 | 所有企业审核状态、有效/停用用户、运营/买方/卖方及只读角色；至少两家可交易企业、一家无业务企业及跨企业隔离案例 |
| 品类与规格 | 所有已实现品类，每种 schema 的必填/可选字段；铜之外的钢材、农产品等实际品类，未知规格键的保留测试 |
| 仓库与单位 | 所有已定义仓库类型/区域、合法无仓库记录、实际支持单位；单位/规格/仓库不匹配及缺关联请求在测试包验证 |
| 库存与预留 | 全可用、部分/全部预留、订单占用、成交受限、可交易、注销等实际状态；每种预留用途、释放/消耗及总量守恒 |
| 挂牌 | SELL/BUY、FIXED/NEGOTIABLE、AUTO/MANUAL、SELF_PICKUP/DELIVERED，以及 OPEN/PARTIALLY_FILLED/FILLED/CLOSED/EXPIRED 等实际状态 |
| 订单与取消 | 所有实际主订单状态；待确认撤销、拒绝、超期、成交取消申请/同意/拒绝；全额、部分、重复与并发转换 |
| 合同与交收 | 每种合法合同状态，未签/单方签/双方签/终止；发货、收货及与取消冲突；正常与有风险的合成条款 |
| 模拟资金 | 各种实际账户/冻结/流水类型和 IN/OUT 方向，零余额、合法操作、余额不足与非法精度；不虚构已实现订单支付 |
| 行情与待办 | 多日期、多品类、有/无成交、不同单位、待确认与取消排除、分页；双方不同待办和完成后消失 |
| AI 会话与工具 | 新会话、多轮、跨会话、无工具、单工具、多工具、无资料、无权限、工具失败；每个注册工具至少一个可核对案例 |
| 知识与检索 | 所有实际文档类型/权限/生命周期；可命中、同义表达、多片段、无答案、旧版本、重复、冲突、删除/更新和引用定位 |
| 导入运维 | 空库、已导入、数据冲突、schema 不匹配、文件损坏、半途失败、向量未建/失败/恢复 |

上表中的名称是现有行为及拟定业务范围，不预先认定建设后的枚举一定沿用。覆盖检查读取最终定义并做差异校验；不合法的组合（例如 BUY+MANUAL）作为拒绝测试，不插入违反约束的正常数据。空对象、非法数量与越权输入以请求用例保存，不关闭数据库约束强行入库。并发缺陷必须由两个实际并发请求/事务验证，静态插入“并发状态”不能替代测试。

覆盖文件必须关联：场景编号、记录编号、角色、页面入口、操作步骤、顾问示例问题、预期工具、知识来源及数值断言。最终验收要求实际类型/状态/合法转换清单没有未解释缺口；有意不支持的业务组合必须明确拒绝并测试。

### 9.4 知识语料与 AI 演示数据

人工维护的中文规则、FAQ、字段/单位说明、交易取消政策和合同条款模板作为必要输入纳入 Git；合成合同实例、分块、散列记录、Embedding 和索引由容器生成，不纳入 Git。规则与实际实现同版本，运行文档带 docId、标题、版本、生效范围、可见性与原文散列；私有合同和企业资料关联所属身份，不与公共规则混成无权限的向量库。

语料处理顺序为：校验原文 → 规范化 → 切块 → 保存 docId/version/chunkId 与定位 → 建立关键词索引 → 用真实 EmbeddingModel 构建向量 → 检索验证。保持标题和条款上下文，调整 chunk size/overlap 并记录配置；同一原文和配置可复现块。没有模型服务时业务与知识文本仍可导入，关键词可演示，向量阶段明确标为未构建。

不把已有机器生成的向量作为跨模型通用向量。向量缓存必须绑定模型标识、版本、维度、原文及分块散列；变更后失效重建。更新/删除同时处理关键词和向量可见性，避免引用旧规则。

每个 AI 演示问题有可查证的 ground truth，包括允许访问范围、必要工具/参数、正确单位与数字、必要来源、预期拒答或故障。至少覆盖“我的库存”“可交易挂牌”“待办与订单”“合同风险”“平台规则”“行情比较”“库存+挂牌+规则综合建议”“越权拒绝”“资料不足”。答案措辞允许变化，事实和权限不得变化。攻击语料、故障返回和互相矛盾文档只在隔离评测包启用。

不预灌假模型回答、假工具轨迹或假 Token 统计作为成功演示；原有会话案例若用作 UI 测试，必须标注测试样例，真实效果由实际调用产生。

### 9.5 克隆后的懒人入口与单步脚本

最终提供三类一键入口：setup-demo.cmd 完成首次准备到启动；import-data.cmd 在环境就绪后导入数据；start.cmd 日常启动，并在首次本地演示使用时委托同一导入流程。三个入口共用步骤实现，不复制逻辑。

首次流程为：检查 Docker/配置 → 准备工具/应用镜像 → 启动 MySQL/Redis → 结构迁移 → 在 data-tools 中生成并校验数据包 → 导入业务 → 导入知识/关键词 → 验证数据 → 启动前后端 → 显示账号、场景、AI 配置和向量状态。已配置真实 Embedding 服务且显式请求构建时再执行向量阶段；默认数据生成是确定性程序，不产生模型费用或下载大模型。

每个步骤同时提供 .cmd 双击入口与 .ps1 参数入口；独立执行会检查前置条件，并指出应先运行的脚本。拟定命令如下，正式 README 必须与最终脚本一致：

~~~powershell
# 首次一键使用；最终在容器中生成并导入完整 demo 包
.\setup-demo.cmd

# 数据一键导入与状态查看
.\import-data.cmd
.\data-status.cmd

# 分步骤操作；同名 .cmd 入口也放在 scripts/data 下
.\scripts\data\check-environment.ps1
.\scripts\data\start-infra.ps1
.\scripts\data\migrate-schema.ps1
.\scripts\data\prepare-dataset.ps1 -Dataset demo
.\scripts\data\import-business.ps1 -Dataset demo
.\scripts\data\import-knowledge.ps1 -Dataset demo
.\scripts\data\verify-dataset.ps1 -Dataset demo
.\start.cmd

# 具备真实 Embedding 配置后单独运行，可按失败块继续
.\scripts\data\build-vectors.ps1 -Dataset demo -Resume
~~~

导入器和生成器通过固定工具容器/应用导入作业运行，脚本解析自身目录、支持中文/空格路径；MySQL 密码经安全配置传入，不拼接进可打印命令。Windows .cmd 的退出码和失败窗口规则与启动脚本一致。GitHub ZIP/clone 同样包含全部重建输入，不含生成结果也能完整初始化，不依赖未初始化的 submodule。

### 9.6 插入、幂等与中断恢复

SQL 模板按依赖组织：身份/权限及基础数据 → 完整库存交易场景（含来源目标、预留、订单、合同与日志）→ 模拟资金/行情支撑 → 知识文档与分块。容器渲染的带实体值 INSERT 只放 .local/data，不纳入 Git。跨表场景按一致性边界提交，不能先插成交订单又漏掉目标库存。

实施要求：

1. 导入前校验 manifest、散列、数据结构、ID/业务编号唯一性、外键引用、数量/金额/权限与 schema 兼容版本；异常停止，不关闭外键或数量约束。
2. 数据集使用独立业务编号/导入归属，数据库导入台账记录 dataset/version/hash、批次时间锚、步骤、scenarioId、提交行数和状态。相同数据版本/散列已成功则核验台账和兼容性并跳过；同版本内容变了或同业务编号已有人工数据则报告冲突，不以 INSERT IGNORE/REPLACE 掩盖错误。初始 expected 用于刚导入或隔离重建的验收，不能要求演示用户操作后的订单仍保持初始状态。
3. 导入锁阻止一键脚本和单步脚本同时导同一批次；重复执行不重写用户操作后的库存、订单或密码。minimal 切换到 demo 使用显式兼容升级包或新的空演示库，不能互相覆盖。
4. SQL 数据插入使用 InnoDB 事务；每个完整业务场景/受控批次与成功台账同事务提交。当前批次失败回滚；成功前序批次保持并可继续。不能宣称全部 DDL 可回滚，结构迁移失败按 Flyway 诊断与备份恢复处理，禁止自动清库或无判断 repair。
5. 恢复依据数据库台账校验已提交数据，不能只看本机“完成”文件。断连/进程崩溃后先确认批次是否提交，再重试，防止提交成功但客户端没收到结果时重复插入。
6. .local/logs 保存脱敏步骤日志和报告，失败提示步骤、场景/文件、可确定的原因、未完成范围及继续命令；退出码区分成功、依赖缺失、校验失败、冲突与执行失败，映射写进文档。
7. 向量为独立可重试阶段，按文档/块记录成功与失败，进行有上限的超时/重试；服务恢复后仅补缺失或失效块。向量失败不回滚已正确导入的业务/知识文本，也不被显示成 RAG 完整就绪。
8. 数据包更新走版本化升级和新批次，先备份并验证兼容；删除/重置只针对确认过的本项目演示库，禁止自动删除未归属导入器的用户数据。
9. 导入期间以项目维护状态阻止业务写入、后台超期扫描和异步通知干扰，完成验证后恢复；早期独立导入可先停止相关应用服务。仅锁住导入器不足以阻止应用竞争。脚本迁移和应用启动迁移共用版本与数据库锁，不同时运行两套无协调的建表逻辑。
10. 参数化 SQL 由容器内导入器绑定时间锚、类型和值，禁止将文本、路径或密码直接拼接成 SQL/命令；schema 结构脚本、业务插入与向量构建各自状态明确。

错误提示示例：

~~~text
[失败] 业务导入：场景 TRADE-SELL-PARTIAL 校验未通过。
原因：目标库存数量与货权记录不一致。
结果：当前场景已回滚；前序已提交场景保留。
下一步：修正数据文件并重新校验，查看 data-status.cmd。
继续：scripts\data\import-business.ps1 -Dataset demo -Resume
日志：.local/logs/本次导入日志
~~~

错误信息中的原因和回滚结果均来自实际验证；网络结果不确定时先显示待核验，不能直接承诺“已回滚”。修正数据必须生成新内容散列及合适版本，不篡改已成功批次。

### 9.7 数据交付验收

- 在新的空 Compose 项目从干净 clone 测试一次 setup-demo：无本机 Java/Node/Python，无作者私有文件，导入后账号可用，所有业务场景和顾问问题有对应记录。
- 比较 .local 中的生成文件、渲染 SQL、数据库记录与运行 expected，核验行数、关联、守恒、成交统计、可见性及知识版本；覆盖检查通过，并检查生成前后 Git 没有新增数据、日志、截图或无关文件。
- 演练每个单步入口、完整重复执行、导入中断/断连、损坏文件、并发导入、schema 不兼容、人工数据冲突及恢复继续。
- 停止/重启不重复灌数据；缺聊天/Embedding 配置时准确说明可用范围；配置服务并执行真实向量构建后有可验证的引用检索。
- 场景说明区分只读展示和可操作数据；完整演示后可以在新的隔离库复现原始数据，不静默重置当前库。
- 数据说明、首次快速启动、分步导入、恢复、账号角色及 AI 演示问题均为中文并实际可执行。

## 十、Spring AI、LangChain、Agent、知识库与 RAG 主线

### 10.1 学习路线与架构职责

主线按“Spring AI 接入 → 身份与会话 → 单工具 → 知识入库与检索 → RAG → 多步 Agent → 合同审查 → 评测与演示”递进。先使用一个受控的顾问 Agent，建立可观察的决策/工具执行循环；多 Agent、微调、MCP 和复杂部署不作为本轮完成前提。

| 层 | 核心职责与可学习成果 |
|---|---|
| 模型接入 | Spring AI BOM/Starter、ChatModel/ChatClient、配置隔离、真实请求形状与响应统计 |
| 顾问请求与记忆 | 身份/企业/会话、系统规则、历史窗口、持久化、清空与切换；用户不能自行指定任意企业 |
| 工具执行 | Spring AI ToolCallback 或所选版本支持的工具机制，参数 schema、服务权限、结构化结果及预算 |
| Agent 编排 | 受约束的多步查询、检索、合并证据、给出答案；每步终止条件、错误与轨迹可观察 |
| 知识库 | 原文、版本、可见性、分块与索引状态，文本和向量来源可追溯 |
| RAG | 查询处理、召回、融合、上下文组装、带依据生成与引用校验；无资料时有明确结果 |
| 效果与展示 | 数据/工具/引用的事实断言、真实模型重复运行、阶段对照和中文演示 |

固定经过核验的 Spring AI 版本，不盲目沿用旧项目 1.0.0 或猜测新版本 API。实施时对照所选版本官方文档验证 ChatClient、记忆 Advisor、工具循环、EmbeddingModel 和检索接口；依赖兼容检查、实际消息形状和工具参数请求都有验证。代码通过明确接口分离供应商适配，首个适配可复用已验证提供商，其他提供商作为独立功能提交。

### 10.2 Spring AI 接入、记忆与可靠性

- 显式配置模型名、端点、超时和启用状态；缺配置显示顾问未配置。连接验证由显式命令触发，不能用 Key 存在认定模型健康。
- Prompt 模板和版本可追踪，稳定系统规则与动态身份/问题分开构造；捕获实际消息请求验证。知识正文、历史用户消息和工具结果属于资料，不能改写系统权限。
- 通过 Spring AI 记忆机制或兼容的记忆实现管理多轮上下文，持久化按 user/enterprise/conversation 隔离；窗口裁剪保留系统约束和必要工具配对，不把无限历史送进模型。
- 会话删除/清空、模型超时、切换身份、并发消息和前端乱序有明确行为；一次请求的运行上下文有开始/结束生命周期，不依赖同步 ThreadLocal 能自然跨线程。
- 工具自动执行与显式 Agent 循环选定一种主控制路径，不能两层各自重试/执行同一工具；若使用框架内循环，必须验证能限制轮数与耗时，否则采用所选版本支持的显式控制。
- 初始试验预算可设每轮最多 8 次工具调用、至多 1 次额外回答重试，并配置总时限、单工具时限、历史/输出/上下文大小；以真实基线调整。超限在执行控制点终止，不能只靠 Prompt 提醒。
- 重试保留系统规则和完整本轮证据；失败查询不能变成空库存。显示轨迹中的截断文本不作为重试上下文；统计包含重试，无法获得全量时标注部分统计。
- 模型超时、无权限、工具失败、无资料、无最终答案和预算耗尽分别记录。记录 requestId、失败阶段、模型/Prompt 版本、工具、引用、耗时及可获得 Token；未知字段为未知。
- Prompt Caching 仅在供应商与版本明确支持时配置，记录实际返回字段；没有命中证据不宣称效果，不把缓存 Token 的 null 变成 0。

### 10.3 工具调用与合同审查

- 业务工具返回有边界的结构化结果，包含数据范围、统计期间、数量单位和必要来源；模型权限来自服务端身份，不接受任意企业范围。
- 工具注册列表、状态接口和测试共用同一真实配置；合同正文工具继续由显式审查意图开放，并对具体合同再次验证权限。
- 系统消息与调用方信息实际请求形状通过请求捕获验证；不会仅凭注释认定缓存或身份边界已实现。
- 重试保留系统约束和工具依据；无法取得完整工具上下文时明确失败。截断的展示轨迹不能代替完整上下文。
- 限制工具次数、重试、超时与结果大小；工具失败、无资料和无权限分别返回明确状态。
- 保存本轮 requestId、工具轨迹、失败阶段、耗时和可得到的 Token 统计；未知缓存指标保持未知，不转成零。
- 首版使用完整 HTTP 回答与明确处理状态；可靠性通过后再独立实现流式输出，并验证安全上下文、取消和记录生命周期。
- 本轮工具保持只读：库存、挂牌、订单、合同、行情、企业、待办、知识；不新增充值、下单、签署或取消写工具。企业范围由服务端校验，权限边界不能只靠模型拒答。
- 记录各工具的数据流、参数/返回结构、查询经过 Service 还是 Mapper、权限所在位置及示例；每个真实注册工具有覆盖案例。工具输出有行数/分页与单位，不返回无限全表内容。
- 合同审查结果分别展示条款原文、定位、风险解释和建议核对项；不把模型意见伪装为系统业务判定或法律结论。

### 10.4 Agent 编排与演示场景

Agent 的完成标准是能在受控循环内选择适用工具、接收结果、决定继续或结束、组合证据并回答；不能仅把一个 ChatClient 类命名为 Agent 就视为完成。

至少实现三条实际多步场景：

1. “我的可用库存能匹配哪些挂牌”：读取本企业库存 → 查询相关挂牌 → 校验品类/单位/规格/仓库和数量 → 输出有来源的候选及不能匹配的原因。
2. “这笔订单下一步该做什么”：读取有权限的订单/合同/待办 → 检索有效业务规则 → 解释当前状态与人工可执行操作；顾问不代签或改状态。
3. “比较合同条款与平台规则”：确认显式审查意图及合同权限 → 读取合成原文 → 检索对应有效条款 → 提出有定位的差异与风险；未覆盖事项明确说明。

框架内部逐步工具选择与确定性业务校验分清职责；单个工具能返回完整答案时不为展示 Agent 人为增加调用。轨迹展示工具名、状态、耗时、引用和可脱敏摘要，不展示模型隐藏推理。终止条件覆盖最终答案、无资料、无权限、异常、用户取消和预算耗尽。

离线测试用模型替身构造指定工具序列、非法参数、反复调用、工具失败、无答案及恶意知识指令；真实评测验证自然问题下工具选择和最终事实，不把替身固定序列的通过率当成模型自主能力。

### 10.5 知识库与 RAG 实现

- 平台规则从统一中文内容生成或导入，保留文档编号、版本和分块来源。
- 比较关键词、向量和混合 RRF，按标注来源计算 Recall@4；融合分数只作排名，不当可信度概率。
- 更新文本后使旧 embedding 失效并补算新向量；空检索、服务不可用和不相关片段不能被当成确定答案依据。
- 公开规则页面与运营知识维护页面分开；维护按钮和服务端权限一致。
- 知识生命周期、导入/分块/索引版本和故障恢复遵循第九节，公共规则和私有合同检索均在召回阶段落实权限过滤；不得先取出私有全文再让模型决定是否可见。
- 使用 Spring AI 的 Document/EmbeddingModel 和兼容检索抽象；存储适配可沿用经过验证的 MySQL/本地方案，规模与耗时通过数据测量，VectorStore 迁移不成为必需的炫技任务。
- RAG 既有显式流程，也有 Agent 可调用的检索工具，两者共用检索服务与来源结构。只有“检索 → 将真实片段放入模型上下文 → 生成 → 校验引用”完整执行才显示为 RAG 回答。
- 关键词、向量、混合 RRF 在同一语料和问题集做对照；记录分块、候选数、topK、融合参数、正确 chunk ID、命中排名、耗时和未命中。混合是否更好依据结果判断，不预写结论。
- 召回与生成分别评分：检索漏召回、命中后错答、错误引用和事实编造分别归因。引用必须属于本轮可见的片段，并可打开对应原文版本和位置。
- 无资料、过期或冲突规则给出对应状态，不使用无关片段强答；RRF 分数不当相关性概率。如加入拒答阈值，单独校准误拒绝与误接受。
- 文本中的“忽略系统要求”等提示注入不得改变工具权限；删除、版本切换、跨企业检索与关键词降级均有回归测试。

### 10.6 测试层次与评测

| 层次 | 工具/环境 | 主要覆盖 |
|---|---|---|
| 纯单元测试 | JUnit/Mockito、前端单元测试 | 状态、精度、参数、触发规则、结果格式和消息组装 |
| 数据库集成 | compose.test.yml 隔离 MySQL/Redis 与工具容器 | 事务、版本冲突、约束、真实 SQL、迁移与审计 |
| 前端交互 | 组件测试 | 表单、缓存、响应乱序、状态反馈和权限呈现 |
| 端到端 | 浏览器自动化与合成账号 | 登录、库存、交易、签约、交收、顾问与启动联调 |
| AI 离线测试 | 模型与 Embedding 替身 | 工具选择边界、异常、预算、重试上下文 |
| 真实模型评测 | 显式评测命令 | 每套引擎至少 60 条各三次，合计至少 360 次；分别记录模型/配置与波动 |
| 启动维护测试 | 隔离 Compose 项目 | 首次/重复/失败启动与导入、恢复继续、数据保留、备份恢复 |

至少 60 条 AI 用例初稿：单工具 12、RAG 14、多步 Agent 10、合同审查 8、隔离/对抗 8、故障/边界 8；数量为最低基线，每种实际工具和知识类型都必须有案例，新增类型时继续增加，不能用 60 条掩盖缺口。固定问题、数据版本、身份、工具范围、必要事实/引用和拒答条件，不要求措辞逐字相同。

先选择约 10 条典型用例建立 Spring AI 最小闭环基线，每次关键修复保留前后对照；LangChain 完成后使用同一题集补基线。正式至少 60 条用例在每套引擎上各运行三次：每套至少 180 次问答，两套合计至少 360 次，工具循环还会产生更多模型请求。先估算两套真实用量并分别设预算，未完成的运行明确标注；普通检查不默认调用模型。

初始目标：隔离和故障测试全部通过；适用用例的必要工具选择至少 90%；有覆盖问题的 Recall@4 至少 85%；演示的数字、单位和引用全部可核对。报告保留样本数、失败和重复运行波动，不将小样本分数宣称为生产保证。

补充要求：记录 p50/p95 总耗时、模型/工具耗时及平均 Token，首轮先建基线再定优化目标；多步问题同时核对来源组合和最终数字。人工事实清单用于开放回答评分，可选模型裁判只作补充并记录分歧。分类记录环境、导入数据、检索、工具选择、上下文、事实和呈现错误；不得删除失败案例制造通过率。

单元测试不依赖外部数据库/模型，集成与评测使用独立 MySQL/Redis 并关闭会扰动用例的扫描和演示初始化；旧项目因 MySQL 不可用而未执行的测试必须重新验证，不能沿用旧通过数量。框架、模型、Prompt、语料/数据、分块/检索与工具配置均进报告，密钥不进报告。

### 10.7 学习与演示验收

约 10–15 分钟的核心演示：从已导入数据登录 → 本企业库存工具查询 → 多轮上下文追问 → 库存/挂牌多步 Agent → 平台规则 RAG 引用 → 显式合同审查 → 越权拒绝 → Embedding 故障关键词降级 → 展示检索对照与真实评测。

每步在同一计划指定场景数据上可复现，页面能查看工具及原文。学习说明对应具体代码入口和真实命令，清楚解释 Spring AI 请求、工具循环、知识入库、RAG、数据权限与评测；只读替身演示可验证软件流程，但只有真实模型运行才计入 AI 效果验收。完成核心展示前不以流式、多 Agent 等扩展替代基础可靠性。

### 10.8 两套独立顾问与统一入口

Spring AI 和 LangChain 都是本轮必做的真实实现。Spring AI 在 Java 后端运行，LangChain 在独立 Python/FastAPI 容器中运行；Python 服务自己执行 LangChain 模型调用、记忆、工具循环、RAG 上下文与生成，不把请求转发给 Spring AI 生成答案。两套框架各自的调用链可读、可测、可观察。

统一架构：

~~~text
前端顾问页面：选择 spring-ai / langchain
    → Java 顾问网关：验证登录、企业、会话、引擎和预算
        → Spring AI 引擎：ChatClient / Memory / Tools / Agent / RAG
        → LangChain 服务：模型适配 / Memory / Tools / Agent / RAG
    ← 统一消息、状态、引用、工具轨迹、耗时与实际引擎

两套引擎的业务工具与知识检索
    → Java 受权限约束的工具/检索服务
    → 同一业务数据与同版本语料、可见性及来源
~~~

Java 后端继续作为唯一业务权限入口，统一结构迁移、业务写入、会话/运行记录和知识来源；Python 服务没有跨企业直连数据库查询权限，也不复制一份交易业务实现。共享的是可信数据、权限和检索接口，各自实现的是框架调用、工具绑定、Agent、记忆适配和回答生成。

#### 10.8.1 统一接口与能力状态

人工维护 contracts/advisor-api.openapi.yml，至少定义：可用引擎、创建/读取会话、发送问题、取消运行、读取工具轨迹与引用。标识固定为 `spring-ai` 和 `langchain`，不能依靠显示名称路由。

共同请求字段包括 conversationId、engine、modelConfigId、message、requestId；默认模型使用明确的系统配置标识，不传默认 Key。响应包括 conversationId、runId、engine、status、content、sources、toolCalls、usage 和 timings，模型元数据仅返回安全字段。具体命名在 C50 固定到契约，C60 补个人配置；未知统计保持 null。

- 创建会话时绑定引擎；发送问题时网关校验请求 engine 与会话保存值一致，不接受客户端伪造其他用户/企业/会话。
- 引擎状态分别报告服务就绪、模型配置和已验证连接状态；服务可达不等于模型可用。Java 应用在任一引擎未配置时仍可启动。
- 网关对引擎路由有明确接口；Spring AI 模型配置不能作为启动整个业务后端的必要条件，LangChain 的独立模型配置同样不能隐式启用另一引擎。
- 默认模型由后端统一配置，两套引擎按兼容适配实际调用；LangChain 不再维护与产品默认值无关的一套隐式默认。个人模型解析与密钥保护按 10.9 执行，配置选择与引擎选择是两个独立维度。
- 未配置、超时、不可达、工具失败、无资料和预算耗尽都有统一分类及引擎来源。不得静默切换到另一引擎并仍显示原选择。

#### 10.8.2 LangChain 学习与实现要求

采用实施时核验的稳定 LangChain/Python 版本和对应模型适配，依赖写进 pyproject.toml 与锁文件。按该版本真实支持的 message/tool/agent/retriever 接口实现，不在计划里锁死过时类名；需要 LangGraph 状态控制时作为 LangChain 实现的明确依赖与学习点说明，不额外要求多 Agent。

| 能力 | LangChain 必须独立完成的内容 |
|---|---|
| 模型与 Prompt | 模型适配、系统/用户/工具消息、Prompt 版本、实际请求捕获与响应统计 |
| 多轮记忆 | 消息窗口与角色映射，按身份/企业/engine/conversation 隔离，持久化使用统一会话接口 |
| 工具 | 将同一工具契约绑定为 LangChain 工具，类型校验、调用网关、结构化输出与错误 |
| Agent | 真正的多步选择/执行/接收结果/结束循环，复现 10.4 的三类场景，有硬预算和取消 |
| RAG | LangChain 检索适配把公共检索结果映射为文档，组装有来源上下文，生成并核验引用 |
| 合同审查 | 显式意图开放正文工具、逐合同权限校验、原文定位、规则对照与风险表达 |
| 诊断与故障 | 各步/工具/重试/用量记录、无答案处理、超时/服务错误、生命周期清理 |

公共检索服务提供受权限约束的关键词/向量/混合结果，便于两个框架在相同上下文上比较生成；Spring AI RAG 与 LangChain RAG 分别组装消息、调用模型和校验输出。报告注明共用召回服务，不能把这种基线宣称为两套底层召回算法之争。以后探索独立召回实现时再单独定义等价语料/权限/指标，不本轮复制两套无法对齐的知识数据库。

#### 10.8.3 内部授权与工具边界

Java 网关为 LangChain 每次运行签发短期、受限的内部委托上下文，绑定用户/企业、权限版本、engine、runId、conversationId、用途/受众与截止时间；不把用户输入的 enterpriseId 当授权，也不向浏览器暴露内部凭证。Python 接口校验受众与签名，工具网关重新核验当前用户/企业状态和权限。

每次工具调用使用当前运行的授权；过期、已取消/结束运行、冻结企业、权限撤销或篡改上下文全部拒绝。工具仍只读，不能绕过权限凭证用 Python 直连读取数据。内部授权密钥走容器配置且不入 Git。传给模型的工具文本不能覆盖这些服务端约束。

统一 toolCallId/运行预算控制避免重复回调无限执行；只读重试按实际权限重新校验，回放结果不能绕过权限撤销。LangChain 服务失败不丢掉网关的失败运行记录，后续请求不得继承上一轮临时上下文。

#### 10.8.4 前端选择与会话行为

新会话默认 Spring AI，选择器明确展示 Spring AI（Java）和 LangChain（Python），显示各自可用状态及失败原因。选择新引擎时打开该引擎新会话或回到其已有会话，不把当前历史悄悄移给另一套实现；已有会话始终显示原引擎。

请求未结束时切换引擎不改变正在执行的 run；取消按原引擎/原 runId 路由。响应按 userId/enterpriseId/engine/conversationId/runId 归属，查询键包含引擎，迟到回答不能写入另一个会话或引擎。账号切换仍清理身份缓存。

两套都支持示例问题、工具轨迹、引用原文、耗时、真实用量和处理状态；缺字段清楚显示未知，不为了对齐 UI 编造值。普通一次提问只执行所选引擎；并排比较是显式实验操作，不自动双倍调用。不可用选项说明原因，保留当前用户选择，不伪装成另一引擎完成。

#### 10.8.5 双引擎对照与最终验收

同一个数据/知识版本、隔离快照、身份、问题、允许工具和事实清单在两个引擎各跑三次，分别记录工具选择、事实/引用、拒答、故障、预算、耗时与 Token。尽量使用同一个兼容模型、提供商与模型参数；无法对齐时明确展示差异，不能把模型差异归结为框架优劣。

共有检索基线可在同一索引上评测一次，两个回答/Agent 执行链必须分别评测。每套引擎都要满足权限与故障硬约束，不能以另一套成功或合并平均分抵消缺陷。两套均可完整演示 10.7；运行结果、历史会话与生成数据仍只存 .local/数据库，Git 只保存必要的比较结论、用例/断言与代码。

### 10.9 后端默认模型、前端个人 API 与隐私

#### 10.9.1 配置和选择

前端提供“平台默认模型”和“我的模型配置”。平台默认模型由部署者在后端 Docker 配置/secret 中设置提供商、协议适配、模型、端点和密钥，用户不填 Key 就可使用已配置的默认模型。计划不附带真实密钥或免费额度，也不把未配置的默认模型写成可用；首次脚本清楚说明平台默认服务状态。

个人配置包含名称、受支持的提供商/协议、HTTPS API 地址、模型 ID 和 API Key，以及有边界的生成参数。首版支持经两套引擎实际验证的提供商适配及 OpenAI 兼容协议，不宣称任意 API 都能使用。工具调用/上下文窗口/响应格式等能力按模型实际验证标注；不支持 Agent 所需工具调用的模型明确限制功能，不能默默换模型。

保存配置只执行格式与安全校验，不发模型请求；“测试连接”是独立显式动作，先说明会向该端点发送最小测试请求并可能消耗额度，测试不携带企业数据或聊天历史。配置错误返回经过清洗的原因。展示可用模型列表需适配服务商是否支持，支持手工填写并验证模型 ID，不把获取列表成功当作 Agent 能力已验证。

新会话选择引擎与模型，绑定 modelConfigId 及安全的配置版本/模型快照。配置变更在后续运行按明确规则生效，每次 run 记录实际引擎、模型和安全端点标识，不能中途改写已发请求。用户切换模型可新建会话；不自动把原会话的敏感内容发给新提供商。删除/失效配置后相关历史仍可读取安全文本，新问题明确要求选择可用配置。

#### 10.9.2 密钥保存与用户隔离

- 个人配置只属于当前用户；前端不提交任意 ownerId，服务端在创建、查看、更新、连接测试、选择、删除与运行时均校验所有权。其他企业成员、管理员页面和其他用户的运行不能读取或借用个人 Key。
- 用户输入 Key 仅经同源配置 API 传到后端，后端用具备认证的加密（如 AES-GCM）保存，独立随机 nonce、密钥版本和与所有权绑定的附加认证数据。主密钥从 Docker secret/受保护配置注入，与数据库/备份分离，不写源码、镜像、生成数据、Git 或普通数据库字段。
- 查询配置只返回 hasKey、掩码、名称、适配/模型和状态，没有任何“查看明文”接口。更新时“保持旧 Key”“替换 Key”“删除配置”明确区分，不能把掩码当新 Key 保存。
- 浏览器仅在输入/提交时短暂处理 Key，不持久化到 localStorage/sessionStorage/IndexedDB、URL、查询缓存或埋点；提交后清空输入，刷新页面只看到掩码。表单不经第三方分析/错误收集传输，前端调试日志不打印请求体。
- 系统默认 Key 和个人 Key 不进入 Prompt、聊天历史、工具参数/返回、轨迹、错误堆栈摘要或 HTTP 调试日志；代理、模型 SDK/回调、重试、连接测试和评测统一脱敏，自动化测试以 canary 验证无泄露。
- 每次运行的模型客户端按身份/配置版本创建或安全缓存，禁止修改全局单例 Key 导致用户串用。缓存短期且可撤销，删除/轮换立即禁止新运行；取消中的已发请求尽力终止，不能声称撤销供应商已经收到的请求。
- 删除配置使密文和运行时缓存不可再使用；说明历史备份中的密文遵循备份保留/轮换策略，不宣称删除当前行就抹除了全部历史备份。提供配置删除、会话删除和可配置保留周期，备份与运行数据都不进 Git。

#### 10.9.3 两套引擎如何使用凭证

Java 网关统一解析授权配置，Spring AI 在服务端使用短生命周期的解密值。LangChain 通过内部模型访问代理使用一次运行/配置绑定的短期令牌，代理将请求发送至已验证的实际提供商，个人/默认 Key 仅在代理端按授权注入。Python 服务和业务工具无需获取长期 Key；令牌禁止访问其他模型配置，绑定 run、用户、受众、过期和预算。

模型访问代理只处理鉴权、出站限制、供应商适配和用量/错误保护，不调用 Spring AI 代做回答、工具循环或 RAG；LangChain 仍独立运行模型/Agent 链路。选择的首批协议必须能通过代理完成真实工具消息往返；不兼容协议明确拒绝，不临时以明文 Key 转交 Python 绕开设计。代理日志不保存 Authorization、原始请求全文或供应商原始错误体。

#### 10.9.4 自定义端点与数据发送边界

个人 API 地址属于服务端出站输入。默认允许经校验的公网 HTTPS 端点，拒绝 URL 内嵌凭证、非 HTTP 协议、非允许端口、localhost/内网/链路本地/云元数据等地址；核验 DNS 解析与实际连接目标（IPv4/IPv6），重定向默认禁止，防止 DNS 变更绕过检查。超时、返回大小与调用次数有上限，不能用测试连接访问 Docker 管理或内部数据库。

部署者配置的本地 Ollama/开发模型使用单独可信内部服务列表，通过 Docker 服务名访问；用户不能借“自定义地址”扩大该列表。Spring AI、LangChain 和模型代理的实际请求都执行相同出站策略，不能只验证保存配置的那一次 URL。

前端明确显示当前模型/提供商，使用前说明发送范围：当前问题、必要历史、本次有权限的工具摘要和检索片段可能发送给所选供应商。仅发送完成问题所需字段，联系方式、令牌和非必要企业字段删除/脱敏；私有合同正文按显式审查意图与权限使用。外部供应商的保留/训练政策按真实服务说明呈现，不承诺平台能控制其全部行为。浏览器到服务器、服务器到外部供应商在部署环境使用 TLS；本机开发入口只绑定 loopback，不能把 HTTP 本地演示称作公网安全部署。

#### 10.9.5 默认服务管理与验证

平台默认模型具备用户限流、并发限制、单轮预算和用量记录，避免一个用户耗尽共享额度；真实可知用量与未知字段区分。默认服务失败时提示当前不可用，用户可主动选择自己的配置；个人配置失败不自动改用平台 Key，防止未经选择的成本/数据发送。

验收包括：默认模型两引擎可用；个人配置 A/B 跨用户/企业及并发隔离；保存不调用模型；连接测试无业务数据；加密字段与主密钥分离；响应/日志/历史/工具/浏览器缓存无明文 Key；删除/轮换撤销；自定义端点 SSRF/重定向/DNS/IPv6；模型能力不足；默认额度限制；引擎与模型切换的迟到响应归属。生成数据只有虚构配置名和无效测试凭证，绝不生成或提交真实 API Key。

## 十三、里程碑与最终验收

按一人熟悉技术栈且模型/容器可用估算约 7–10 周，包含两套 AI 引擎、个人模型隐私、完整数据与故障恢复、UI 和业务回归，实际以验证结果校准。本次不设虚构完成日期；环境、模型及并发修复可能增加时间。早期先拿到 Spring AI 闭环，再实现 LangChain 与共同配置，不等全部业务完成才验收 AI。

### 14.5 统一检查入口与退出码

C01 建立 `check.cmd`/`scripts/check.ps1` 的任务分派基础，C03/C04 等节点逐步注册对应检查。`-Task` 只接受已有 C00–C74，未知任务/模式、未实现必需检查、无效参数全部非零返回，禁止空检查默默成功。

统一拟定接口，工作目录为新仓库根目录：

~~~powershell
# 查看当前环境，检查单个已实现任务
.\scripts\project-context.ps1
.\check.cmd -Task C43 -Mode task -NoPause

# 单独重跑数据库集成或离线 AI 检查
.\check.cmd -Task C43 -Mode integration -NoPause
.\check.cmd -Task C43 -Mode ai-offline -NoPause

# 已完成范围的整体回归，默认不发真实模型请求
.\check.cmd -Mode full -NoPause
~~~

`-Mode task` 执行下表规定的当前任务必需检查。full 检查所有已实现且登记的必需项，并报告覆盖到的最高节点；C74 才能宣称 75 个节点完成。单跑某模式不能替代当前任务其他必需检查，不能把“集成未运行”登记为功能完成。

所有模式支持 `-Engine spring-ai|langchain|both`；两套完成后 task/full 默认核验相关两套离线能力，普通一次 UI 问答仍只执行所选引擎。ai-live 只在显式指定该模式时发真实请求，task/full 只核验既有真实结果与当前代码/模型/数据版本是否匹配；缺有效证据则显示未完成，不自行重复付费调用。

| 模式代码 | 必须实现的检查范围 |
|---|---|
| static | 改动文件格式、目录/注释/配置检查、计划一致性与暂存范围，代码存在后包含类型/lint |
| unit | 与当前任务相关的后端/前端单元测试；无模型与外部数据库调用 |
| integration | 隔离 MySQL/Redis 的真实 SQL、事务/版本/迁移/权限测试，关闭干扰扫描 |
| dataset | 结构、散列、引用、初始数量/金额守恒、SQL 同源、类型/状态/转换覆盖与导入台账 |
| ai-offline | 模型/Embedding 替身下的消息、记忆、工具循环、预算、重试、权限与故障；不冒充真实效果 |
| rag | 同一有版本语料的检索对照/来源断言；需要真实向量时先检查索引，缺少则报未执行 |
| e2e | 已启动隔离平台中的实际接口/浏览器关键流程；查询依据与 UI 状态一致 |
| visual | 对应页面桌面/窄屏、正常/异常、键盘与对比度；截图来自实际运行页面 |
| ops | 首次/重复/失败启动或导入、停止保留数据、恢复、作用域与准确退出码 |
| ai-live | 真实模型用例、次数、身份、事实/引用与用量记录；单独显式运行，不混进普通 full |

每种模式分派到项目真实可运行的 Docker 工具命令，输出版本、退出码与脱敏结果位置；失败保留在 .local，外层不能输出“成功”覆盖子命令失败。不提供要求宿主安装 Java/Node/Python/npm 包的替代流程；PowerShell 仅做参数、文件、Git 与 Docker 编排。

拟定统一退出码：0 成功，2 参数/入口未实现，3 环境/前置条件未就绪，4 数据/schema/断言校验失败，5 数据归属或并发导入冲突，6 执行/超时/网络异常。子工具原始错误码另存日志，不能以统一码抹去原因；.ps1/.cmd 都明确传播退出码，双击保留错误窗口，`-NoPause` 自动化模式立即返回。

Docker 工具服务在 C02 建立 Compose 定义，C03/C04/C06/C16 分别补实际后端、前端、数据和评测内容，C05 完成应用运行镜像。以下是各节点实现后可以采用的完整命令契约，工作目录为新根目录，脚本自动检查镜像/文件与版本；容器中的命令不在宿主执行：

### 14.8 提交、异常与跨会话续作

任何任务都按以下顺序收尾：更新相关使用说明 → 完成本节必需检查 → 审阅实际 diff → 明确暂存本次文件 → 查暂存 diff 与有效身份 → 中文提交 → 查提交及工作区 → 更新续作信息。

新仓库根目录的只读核验命令：

~~~powershell
git status --short
git diff --check
git diff --stat
git diff --cached --check
git diff --cached --stat
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
~~~

按本次真实文件逐项 `git add -- '文件路径'`，不无判断地 `git add .`；提交正文写真实改动/验证/影响，使用 UTF-8 临时提交消息文件和 `git commit --file`，避免多行中文在 Shell 中被拼坏。临时消息在 `.local/`，不附加 AI 身份。提交之后用 `git log -1 --format=fuller` 与 `git status --short` 核验 Author/Committer、内容和剩余改动。不能以 hook 被跳过或只通过格式检查认定业务验收通过。

提交前额外运行 `git diff --cached --name-only` 与 `git ls-files -- '.local'`。暂存清单必须符合 3.5；生产/生成数据、缓存、日志、截图、备份和无关文件一律不暂存，.local 不应出现已跟踪项。有必要的功能断言/生成规则与无意义运行输出严格区分，不能把几百份测试 JSON 当成验证证据提交。每次运行的进度和诊断放 .local；本文仅维护必要当前节点、里程碑及影响后续工作的变更，不为每条命令追加永久流水。

处理分支统一如下：

| 情况 | Codex 下一步 |
|---|---|
| 命令/脚本不存在 | 核对任务前置与文件；完成缺失实现，不猜参数、不伪造测试 |
| 依赖未就绪 | 运行已实现的环境/状态诊断，按具体原因准备服务；缺模型 Key 时继续可独立的离线工作 |
| 检查断言失败 | 保留错误与版本，定位实现或数据，修复后重跑相关检查；不改低门槛遮盖缺陷 |
| 子命令退出码非零 | 停止依赖操作，核对当前修改/事务影响与日志，不提交“已完成” |
| 导入断连/结果未知 | 查数据库台账确认是否提交，按第九节恢复，不直接假设回滚 |
| 工作区有用户改动 | 确认范围，保留用户修改；不 reset/clean 或暂存无关内容 |
| 服务长时间等待 | 使用有上限的健康探测，说明正在等待的具体条件，超时后诊断 |
| 新一轮或上下文恢复 | 读本文当前任务、最近提交/工作区/状态，再继续未完成一步，避免从 C00 重做 |
| GitHub 尚无远程仓库 | 用新仓库干净本地 clone 做等效验收；不为测试自动发布，记录实际来源 |

干净 clone 验收必须用独立绝对路径与 Compose 项目，不复用开发数据卷/配置；不修改现有工作目录。源码/数据输入来自已提交版本，模型 Key 单独按公开配置入口提供，不从开发机私有文件偷取。默认无 Key 路径与真实 AI 配置路径分别验收，结果不能混写。
