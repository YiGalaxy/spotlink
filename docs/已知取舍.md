# 已知的简化与取舍

诚实记录。每一条都写清**是什么**、**为什么这样选**、**代价是什么**——一个只写了
「暂未实现」的清单，演示时被追问一句就答不上来。

---

## 资金与清结算

**资金为模拟实现。** 真实平台由第三方清算机构（如大宗商品清算通）划转，平台不持有
资金池，也不需要支付牌照。这里 `FundService.recharge` 的钱来自虚空，这正是它的
用途——让冻结、支付、退款这条链路可以被完整走通。

**资金账户没有开户流程。** 目前只有演示数据脚本会创建 `t_fund_account`，没有任何
Java 代码在注册或审核通过时开户。结果是**通过接口注册的新企业没有资金账户**。
正确做法是在企业审核通过时开户。

**买方挂牌的保证金从未真正冻结。** `FundService.freezeMargin` / `releaseMargin` /
`payFromMargin` 都存在，`t_order.margin_freeze_id` 也存在，但**没有任何交易代码
调用它们**。规则文档里因此只写「保证金比例由交易中心决定并公告」，不写具体比例——
写了就是让顾问引用一个平台从未收取的费用。

## 交易与交收

**两种成交模式都实现了，发布挂牌时二选一。** 详见 [设计要点](设计要点.md#二两种成交模式发布挂牌时二选一)。

**`MANUAL` 只支持卖方挂牌。** 买方挂牌背后没有预先冻结的货物，要「等确认」就得
保证确认时货还在，平台保证不了，所以数据库层面直接拒绝这个组合。

**交收没有独立的单据表。** `ResultCode` 里有 7xxxx 段交收相关的错误码，但没有交收单
表、没有交收服务——交收就是订单状态的流转（`CONTRACTED → DELIVERING → COMPLETED`），
外加磅差容差写在合同条款里。

**合同没有终止流程。** `Contract.TERMINATED` 这个状态被建模了，但没有任何代码能把
合同变成它。

**库存单没有待审核状态。** `InventoryNote.PENDING_REVIEW` 同理——入库登记直接进入
`IN_STOCK`。

## AI 顾问

**数据出境面。** 顾问的每个工具结果都会进 prompt 并发送到模型端点（默认
`api.deepseek.com`）。这**不是**跨租户泄漏——工具在结构上只能读调用者自己的数据，
且有测试守着——而是**数据离开平台到第三方**的问题。

| 会发出去 | 不会发出去 |
|---|---|
| 合同正文（双方、价格、数量、条款） | **资金余额与流水**（已刻意移除该工具） |
| 库存单、订单、待办 | 任何其他企业的数据 |
| 企业联系信息 | 密码 |

**这是一次有意识的取舍而非疏忽**：合同审查是顾问的核心功能，没有合同正文就做不了。
不能接受这一点的部署，应当把 `BULK_ADVISOR_BASE_URL` 指向自建模型。

**顾问不读资金余额。** 余额是平台上最敏感的数字，而顾问没有任何一项职责需要它。
「没有这个能力」比「有这个能力但拦着」更可靠——`AdvisorTenantIsolationTest` 会
断言它不存在，因为这种能力回归的方式就是有人图方便把它加回来。

**合同正文需要显式触发。** 用户没有要求审查合同时，`get_contract_detail` 根本不在
工具列表里。这是最小化而非访问控制：合同是调用者自己的，判断错方向不损失安全性，
只是少发了一份本可以不发的文档。

**AI 端点为兼容网关。** 代码按 Anthropic 官方 SDK 写，`base-url` 与模型走配置。
prompt caching 的策略已按官方语义实现，但真实效果需官方 API 才能验证。

**模型偶尔只输出英文草稿、不输出答案。** 这是网关侧的行为（推理内容与答案共用同一
通道），提示词约束不住。有两层兜底：`AnswerCleaner` 剥掉推理前缀，`AdvisorAgent`
在没有答案时**收走工具再问一次**。仍然失败时才返回一句道歉，并把原文打进日志。

## 数据库

**向量检索在 Java 端做，不是数据库索引。** MySQL 没有向量类型（9.x 才加，且太新），
所以 `t_knowledge_chunk.embedding` 是 `BLOB`，检索时把全部分块读出来在 Java 里算
余弦相似度。

**当前语料几十个分块，扫描就是索引，而且排序是精确的**——比近似索引还准。失效点是
规模：一万个分块时每个问题要读一万个 blob，那时的解法是换向量库，不是把 `LIMIT`
调大。这是从 PostgreSQL 迁到 MySQL **唯一真正变差**的地方。

**部分索引没了。** PostgreSQL 的 44 个 `CREATE INDEX ... WHERE deleted = 0` 在 MySQL
里不存在，全部退化成普通索引。软删标记因此从索引定义挪进了查询条件——占空间略多，
查得一样快。

**`TIMESTAMPTZ` 没了。** MySQL 没有时区感知类型，改成 `DATETIME(6)`，时区语义从
「每个值自带」变成「整个连接约定 UTC」（见 JDBC URL 的 `connectionTimeZone`）。这要求
**所有写入都走应用层**；有人直连数据库手写 `NOW()` 就会混进本地时间。

**逐条检索的关键词那一路对问句形式不友好。** ngram 分词把「能不能退」切成 2 字
bigram，而正式规则文本里不会出现「能不能」。这类问法只能靠向量那一路覆盖。

## 运维与部署

**定时任务在多实例下会重复执行。** `@Scheduled` 在每个实例上都会跑。当前两个任务都会
重读状态并跳过已完成的工作，不会出错，但需要在规模化之前加锁（ShedLock 或
`GET_LOCK`）。

**JWT 在有效期内不校验租户是否还存在。** 签名密钥换了之后，令牌能继续用满 TTL
（访问令牌 2 小时）。重建数据库时踩到过：浏览器里存着旧后端签发的令牌，带着一个在
新库里不存在的企业 ID，新后端照认不误——于是以幽灵企业的身份写进了挂牌和订单。
**账号状态已经按请求校验**（禁用立即生效），但企业存在性还没有。
