# 数据库约定

MySQL 8.4 · Flyway · 迁移脚本在 `backend/src/main/resources/db/migration/`。

---

## 主键

**雪花 ID，应用生成**（MyBatis-Plus `assign_id`），不用 `AUTO_INCREMENT`。

这样 ID 在将来分库分表时仍然唯一，而且**不依赖数据库**——批处理插入不需要回读生成
的键。

演示脚本用 7.x e18 段的手写 ID，与雪花取值范围错开。**注意 BIGINT 上限是
9.22e18**：`9.2e18` 起步的基数会溢出，而更低一点的基数会回绕成负数，看起来像数据
损坏而不是一个错误。

---

## 金额与数量

| | 类型 | 说明 |
|---|---|---|
| 金额 | `DECIMAL(19,4)` | Java 侧 `BigDecimal` |
| 数量 | `DECIMAL(18,3)` | 吨、千克 |

**绝不用 `float` / `double`。** 二进制浮点误差在金额上是事故，不是精度问题。

金额在订单上是**存储的而不是重算的**（`t_order.amount = quantity * price`，在达成一致
那一刻凝固）：若价格或数量日后被更正，推导出来的总额会无声地改写一笔已经开过票的
交易的历史。

## 审计列

每张业务表都有：

```
created_at / updated_at / created_by / updated_by / deleted
```

- `updated_at` 由触发器维护，应用不可能忘记更新它
- `deleted` 是软删标记（0 存活 / 1 删除），MyBatis-Plus 的 `@TableLogic` 自动过滤

**两个例外，都是有意的：**

- `t_audit_log` **没有** `deleted` 和 `updated_at`。一行能被更新的日志，是证词能被
  编辑的日志；一行能被删除的日志，是被告最想删掉的日志。软删约定在这里恰好是错的
  形状。
- `t_user_role` / `t_role_permission` **没有** `deleted`。撤销一个授权就必须真的撤销，
  否则每条查询都得记着过滤，而忘记一次就会让已撤销的角色继续生效。**授权活得比撤销
  更久，是安全漏洞而不是一条记录。**

**这一族有个共同陷阱**：MyBatis-Plus 的 `updateById` 默认**跳过 null 字段**，所以
「把这一列清空」会被静默地变成「保持原值」。需要清空的字段必须显式声明
`@TableField(updateStrategy = FieldStrategy.ALWAYS)`——本项目在两处踩过。

## 约束

**能写进数据库的规则就不写进 Service。** Service 里的检查可以被人忘掉、被新代码
绕开，约束不会。

例子：

```sql
-- 三量守恒
CHECK (available_quantity + frozen_quantity = total_quantity)

-- MANUAL 仅限卖方挂牌
CHECK (confirm_mode = 'AUTO' OR side = 'SELL')
```

**这需要判断，不是教条。** 一条会随业务变化的规则写进 `CHECK` 就成了迁移的负担；
上面两条都是不变量，变化的方式不是「调整取值」而是「推翻设计」。

## 索引

MySQL **没有部分索引**。PostgreSQL 时代那 44 个 `CREATE INDEX ... WHERE deleted = 0`
全部退化成普通索引，软删标记从索引定义挪进了查询条件。

**全文索引用 ngram 分词器**：

```sql
CREATE FULLTEXT INDEX idx_knowledge_chunk_content ON t_knowledge_chunk (content)
    WITH PARSER ngram;
```

分词器选择是承重的——MySQL 默认按空白分词，而中文没有空白，不加 ngram 整段中文
就是一个 token，什么都匹配不上。

**ngram 的 token 长度默认是 2**，所以单字查询在这一路会返回空。这是已知限制，
向量那一路仍然能覆盖这类问法。

## 迁移

1. **一经执行不可修改**——改结构就新增 `V{n}__xxx.sql`。Flyway 会校验已应用脚本的
   校验和，改了就启动不了。
2. **新脚本必须在真库上跑一遍再提交**，包括跑第二遍确认幂等性（演示数据脚本）。
3. 数据迁移混在结构迁移里时要格外小心：`V8` 把一个状态迁移和一次结构变更写在同一个
   脚本里，而它必须**先写日志行再更新状态**，否则日志里的 `from_status` 已经不对了。
4. Flyway 需要脚本版本连续可读。`V9` 和 `V10` 由不同的人同时编写时，如果其中一个
   失败了，它会留下一行 `success = 0` 的历史记录，之后所有迁移都会被拒——这是
   Flyway 在保护你，不是它坏了。

---

## 时区

MySQL 没有 `TIMESTAMPTZ`。全库用 `DATETIME(6)`，时区语义由 JDBC 连接约定：

```
connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true
```

**这要求所有写入都走应用层。** 有人直连数据库手写 `NOW()` 就会混进本地时间，而
`DATETIME` 不存偏移量，混进去之后无法从数据本身看出来。
