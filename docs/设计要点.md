# 设计要点

一份代码库的形状是它想解决的问题的形状。下面每一条都对应一个具体的实现选择，
而不是一条原则声明——原则不值钱，把它落到哪一行代码上才值钱。

---

## 一、挂牌是要约，摘牌是承诺

**所以没有撮合引擎。** 这不是没做，是不该做。

一个负责发现价格的中央引擎会让交易场所成为期货意义上的交易所；两个具名主体
每次就一份合同达成一致，才是普通的现货交易。`Listing` 的类注释里写着这一点，
`OrderService` 的注释里也写着——因为它决定了这两个类里能写什么、不能写什么。

配套的一条：**电子库存单不是仓单**。仓单在《民法典》里是物权凭证，可质押、可
背书转让。拿物权凭证当标准化交易标的，是现货平台被认定为变相期货的典型路径。
所以这个平台的库存单叫「电子库存单」，`InventoryNote` 的注释里明确写了它不是
什么。

## 二、两种成交模式，发布挂牌时二选一

「发布挂牌算不算挂牌方已经同意」——市场上两种做法都有，区别只在这一件事上：

| | `AUTO` 摘牌即成交 | `MANUAL` 需挂牌方确认 |
|---|---|---|
| 挂牌的法律性质 | 要约 | 要约邀请 |
| 摘牌是什么 | 承诺，合同当场成立 | 提出成交请求 |
| **货权何时转移** | **摘牌那一刻** | **挂牌方确认那一刻** |

**为什么两种都要做**：只做一种，平台就没法解释自己。做 `AUTO` 却说「挂牌方可以
不同意」，等于摘牌不是承诺；做 `MANUAL` 却在摘牌时就过户，等于确认这一步是摆设。

**它是发布时选定的，不是全局开关**——这是要约本身的属性，同一个卖家完全可能一张
挂牌定死价格、另一张要自己点头。

`MANUAL` 摘牌时**不转移货权**，只把数量从挂牌上摘掉（防止第二个买家摘走同一批货）。
于是有一个可验证的不变量：**冻结量恒等于「未成交 + 待确认」的全部货物**。

`MANUAL` 仅限卖方挂牌——买方挂牌背后没有预先冻结的货物，要「等确认」就得保证确认
时货还在，平台保证不了。这条由数据库 `CHECK` 强制，而不是只写在 Service 里。

## 三、数量是三个数

`total / available / frozen`，数据库约束保证 `available + frozen = total`。

挂牌不拿走货，只预留——卖方挂 60 吨，库存变成「可用 40 / 冻结 60」，货主还是他。
这就是为什么数量要拆成三个口径：只看「可用」的话，卖方分不清货是卖掉了还是只是
被挂出去了。

**冻结一张表管两种东西**：商品冻结和资金冻结生命周期相同（预留 → 消耗或释放），
共用 `t_freeze_record` 和一套 `FreezeService`。

**部分消耗靠"关旧开新"而不是改数量**：卖方挂 100 吨，买方摘 30，`consumeInventoryPartial`
把原冻结记录标记为已消耗、剩余量开一条新记录。因为冻结记录是一条「某时刻预留了
多少」的陈述——改写它就抹掉了当时预留了多少，而这恰恰是日后双方争执时要问的
第一个问题。

## 四、订单状态机是一张表，不是一堆 if

```java
private static final Map<String, Set<String>> TRANSITIONS = Map.of(
        PENDING_CONFIRM, Set.of(CONFIRMED, CANCELLED),
        CONFIRMED,       Set.of(CONTRACTED, CANCELLED),
        CONTRACTED,      Set.of(DELIVERING, CANCELLED),
        DELIVERING,      Set.of(COMPLETED),
        COMPLETED,       Set.of(),
        CANCELLED,       Set.of()
);
```

散落的 `if (status == ...)` 会让「合法的流转有哪些」只存在于作者脑子里，每加一个
状态都是一次引入非法路径的机会。写成数据之后，**没列出来的流转就是不可能发生**。

**但表只表达合法性，不表达权限。** `PENDING_CONFIRM → CONFIRMED` 合法，但只有挂牌
方能按这个按钮——买方按下去等于替对方接受了自己的提议。所以有一个按调用者过滤的
重载，同时喂给服务端校验和接口的 `allowedActions`：**前端渲染出来的按钮就是服务端
真的会接受的按钮**。

三个状态对角色敏感，原因只有一个：**双方都能做的步骤就是没人负责的步骤。**

---

## 五、状态之外还有一句「该谁动」

「已签约」不说谁签了，「交收中」不说谁该收货。同一笔送到订单，卖方和买方需要
**相反的两句话**，而两方都无法从这个词里判断自己是不是被等的那个。

```
已签约 送到   卖方「待我发货」  买方「等对方发货」
已签约 自提   卖方「待我放货」  买方「等对方放货」
交收中 送到   买方「待我收货」  卖方「等对方收货」
交收中 自提   买方「待我提货」  卖方「等对方提货」
```

**无论送到还是自提，都是卖方先动**——货没放出来，买方提什么。

`statusHintMine` 单独作为布尔字段返回：客户端排序和标色靠它，不去解析那句话的
措辞。措辞是最容易被改动的部分，靠解析措辞判断的逻辑会在某次改文案时静默失效。

订单列表默认分**三层**：该我动的 → 等对方的 → 已完结。两层不够——对方压着不动的
订单不是「已完成」，埋在已完成里恰好把正在变味的单子藏起来。

## 六、乐观锁防并发

每次数量变动都是 `UPDATE ... WHERE id = ? AND version = ?`。抢不到的拿到零行结果，
被要求重试而不是静默覆盖。

不用悲观锁：这里的锁持有时间是点击一次按钮的时间，而抢锁失败是罕见事件。

**并发正确性有一个测试守着**（`FreezeServiceTest`），因为这类问题只在并发下出现，
而并发问题在开发机上几乎从不出现。

---

## 七、ID 序列化为字符串

雪花 ID 是 19 位，JavaScript 安全整数只有 16 位。`2101635756223557634` 传到前端变成
`2101635756223557600`——**前端回传的 id 指向另一行**。

所以后端每个 id 字段都带 `@JsonSerialize(using = ToStringSerializer.class)`，前端
`EntityId = string`。这条踩过一次，症状是「一直弹出来会话不存在」。

---

## 八、权限码，不是角色

`@PreAuthorize("hasAuthority('admin:enterprise:review')")` 检查的是码，不是
「是不是管理员」。

**为什么**：角色只是一堆权限的集合，检查集合本身会让集合里的内容沦为摆设。审计员
持有全部读取码、零个写入码——「只读」因此是服务端强制出来的事实，而不是对某个
角色名称的承诺。

权限按请求从数据库读（经 Redis 缓存），不塞进 JWT：**JWT 无法撤销**，从 token 里
读权限会让被收回的权限在令牌有效期内继续生效。同一次加载带回账号状态，所以禁用
一个账号在它**下一次请求**就生效，不必等两小时。

---

## 九、租户的边界在结构上，不在约定上

企业 ID **永远**从登录态读取，**绝不**从请求参数读取。

```java
Long enterpriseId = SecurityUtils.currentEnterpriseId();   // 正确
Long enterpriseId = request.getParameter("enterpriseId");  // 错误：越权
```

AI 顾问的工具同样遵守：**没有工具接受企业 ID 参数**，所以模型物理上无法指定别的
企业——提示注入也做不到，因为没有那个入参可以填。

**这一条有两个测试守着，而不是靠注释**：
`EnterpriseIdParameterIsolationTest` 断言 `admin` 包之外没有任何处理器接受企业 ID
形状的参数（包括请求体字段），`AdvisorTenantIsolationTest` 断言顾问工具读不到别的
企业。运营后台的订单查询是全平台唯一的例外，它由 `admin:order` 权限守护。
